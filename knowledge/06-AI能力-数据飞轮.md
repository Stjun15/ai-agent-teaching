> **一句话总结：** 用"私教持续调计划"类比讲清数据飞轮四步循环（收集反馈→分析瓶颈→调整→观察），让 Agent 系统持续进化而非一次性优化。

> **AI角色：老师。** 目标是让学习者在45分钟内掌握数据飞轮：反馈收集→问题分析→数据优化→模型更新→闭环驱动。
>
> **防什么失败？** 防"Agent 上线后质量停滞不前，没有持续优化机制"。防"用户反馈收集了，但不知道怎么用"。防"辛辛苦苦标注了数据，但飞轮转不起来"。

## 为什么需要数据飞轮？

> **真实场景：** 某团队上线了智能客服 Agent，第一周效果不错。但一个月后，转人工率从 10% 慢慢涨到 18%。团队查来查去，发现不是 Agent 变差了，而是用户问题变复杂了——新产品上线后，用户开始问新功能的问题，Agent 的知识还停留在旧版本。团队这才意识到：**Agent 不是上线就完事了，它需要像"活"的系统一样持续学习。** 如果上线时就建好数据飞轮——自动收集差评 Case、每周分析高频失败问题、补充 Golden Case 优化 Prompt——Agent 就能跟着业务一起进化。

**类比：健身房的私教**

```
坏做法 = 私教给你一份训练计划，然后再也不管你了
  → 你练了半年，肌肉没长，体脂没降
  → 为什么？因为身体适应了，需要调整计划，但没人帮你

好做法 = 私教每两周评估一次
  ├── 收集数据：体脂率、深蹲重量、睡眠质量
  ├── 分析瓶颈：核心力量不足？训练强度不够？
  ├── 调整计划：加重量、换动作、改饮食
  └── 观察效果：数据改善 → 继续优化；恶化 → 回退调整
  → 这就是"数据飞轮"——不是一次性的优化，而是持续循环的进化
```

│                                                                  │
│                         ┌──────────┐                             │

│                      │  ┌─────▼────┐  │                        │

## 第二讲：数据飞轮实现

### 2.1 反馈收集

**文件：`agent-platform/src/flywheel/feedback-collector.ts`**

```typescript
/**
 * 反馈收集器
 *
 * 为什么不止收集 👍/👎？
 * 👍/👎 只能告诉你"好不好"，不能告诉你"为什么不好"
 * 必须收集原因（reason）和完整对话上下文，才能做有效分析
 */
export class FeedbackCollector {
  /**
   * 收集单条反馈
   *
   * 为什么同时收集隐式反馈？
   * 用户可能不点 👍/👎，但从行为可以推断满意度：
   * - 追问 3 次以上 → 大概率不满意
   * - 对话中途断开 → 可能是体验太差
   * - 点了转人工 → 明确不满意
   */
  async collect(sessionId: string, feedback: UserFeedback): Promise<void> {
    const conversation = await this.getConversation(sessionId);

    await this.db.save("agent_feedback", {
      session_id: sessionId,
      user_id: feedback.userId,
      rating: feedback.rating, // 'positive' | 'negative' | 'neutral'
      reason: feedback.reason, // 为什么这么评价
      category: feedback.category, // 错误分类：hallucination/timeout/irrelevant
      conversation: conversation, // 完整对话上下文
      agent_answer: conversation.lastAnswer,
      intent: conversation.intent, // 当前意图
      implicit_signals: this.extractImplicitSignals(conversation),
      timestamp: new Date(),
    });
  }

  /**
   * 从对话中提取隐式反馈信号
   *
   * 为什么需要隐式反馈？
   * 大多数用户不会主动点 👍/👎（可能只有 5% 的用户会）
   * 显式反馈 + 隐式反馈 = 覆盖率从 5% 提升到 80%+
   */
  private extractImplicitSignals(conversation: Conversation): ImplicitSignals {
    return {
      followUpCount: conversation.userMessages.length, // 用户追问次数
      abortEarly: conversation.endedByUser && conversation.turns < 3, // 用户提前中断
      repeatedQuestion: this.hasRepeatedQuestion(conversation), // 用户重复提问
      escalatedToHuman: conversation.escalated, // 转人工
      sentimentScore: this.analyzeSentiment(conversation.userMessages), // 情感分析
    };
  }

  /**
   * 周报分析
   * 为什么是周报而不是日报？
   * 日数据量太小，统计波动大；周数据量足够，能看出趋势
   */
  async analyzeWeekly(): Promise<WeeklyReport> {
    const feedbacks = await this.db.query(`
      SELECT * FROM agent_feedback 
      WHERE timestamp > NOW() - INTERVAL '7 days'
    `);

    // 按意图聚合分析
    const byIntent = this.groupBy(feedbacks, "intent");
    const worstIntents = Object.entries(byIntent)
      .map(([intent, items]) => ({
        intent,
        negativeRate:
          items.filter((f) => f.rating === "negative").length / items.length,
        sampleCount: items.length,
        topReasons: this.topReasons(
          items.filter((f) => f.rating === "negative"),
        ),
      }))
      .sort((a, b) => b.negativeRate - a.negativeRate)
      .slice(0, 5); // Top 5 最差意图

    return {
      period: "weekly",
      totalFeedback: feedbacks.length,
      positiveRate:
        feedbacks.filter((f) => f.rating === "positive").length /
        feedbacks.length,
      negativeRate:
        feedbacks.filter((f) => f.rating === "negative").length /
        feedbacks.length,
      topNegativeReasons: this.topReasons(
        feedbacks.filter((f) => f.rating === "negative"),
      ),
      worstIntents,
      trend: await this.compareWithLastWeek(),
    };
  }

  private topReasons(feedbacks: Feedback[], limit: number = 5): ReasonCount[] {
    const counts: Record<string, number> = {};
    for (const f of feedbacks) {
      if (f.reason) {
        counts[f.reason] = (counts[f.reason] || 0) + 1;
      }
    }
    return Object.entries(counts)
      .sort(([, a], [, b]) => b - a)
      .slice(0, limit)
      .map(([reason, count]) => ({ reason, count }));
  }
}

interface UserFeedback {
  userId: string;
  rating: "positive" | "negative" | "neutral";
  reason?: string;
  category?:
    "hallucination" | "timeout" | "irrelevant" | "incomplete" | "other";
}

interface ImplicitSignals {
  followUpCount: number;
  abortEarly: boolean;
  repeatedQuestion: boolean;
  escalatedToHuman: boolean;
  sentimentScore: number;
}

interface WeeklyReport {
  period: string;
  totalFeedback: number;
  positiveRate: number;
  negativeRate: number;
  topNegativeReasons: ReasonCount[];
  worstIntents: IntentAnalysis[];
  trend: TrendComparison;
}

interface ReasonCount {
  reason: string;
  count: number;
}
```

### 2.2 问题分析与 Golden Case 生成

**文件：`agent-platform/src/flywheel/case-optimizer.ts`**

```typescript
/**
 * Case 优化器
 *
 * 为什么需要把错误 Case 转为 Golden Case？
 * 错误 Case 告诉你"什么不行"，Golden Case 告诉你"什么行"
 * 飞轮转起来的关键是：不仅发现问题，还要生成解决方案
 */
export class CaseOptimizer {
  /**
   * 将错误 Case 转为 Golden Case
   *
   * @param errorCase 错误 Case（用户问了什么，Agent 答了什么，为什么错了）
   * @returns Golden Case（用户问了什么，正确答案应该是什么，为什么这样答）
   */
  async convertToGoldenCase(errorCase: ErrorCase): Promise<GoldenCase> {
    // 用 LLM 生成正确答案
    // 为什么用 LLM 生成？
    // 人工标注每个错误 Case 成本太高（$5-10/条），
    // LLM 生成 + 人工审核 → 成本降到 $0.5-1/条
    const correctAnswer = await this.llm.generateCorrectAnswer({
      question: errorCase.userQuestion,
      wrongAnswer: errorCase.agentAnswer,
      errorReason: errorCase.errorReason,
      context: errorCase.context,
    });

    return {
      id: `golden-${Date.now()}`,
      source: errorCase.id,
      userQuestion: errorCase.userQuestion,
      correctAnswer: correctAnswer.text,
      reasoning: correctAnswer.reasoning, // 为什么这样回答是正确的
      intent: errorCase.intent,
      difficulty: this.assessDifficulty(errorCase),
      tags: errorCase.tags,
      createdAt: new Date(),
      reviewed: false, // 需要人工审核确认
    };
  }

  /**
   * 批量生成 Golden Case
   * 为什么批量处理？
   * 单条处理效率低，批量 + 人工审核管线是工业级做法
   */
  async batchGenerateGoldenCases(
    errorCases: ErrorCase[],
  ): Promise<GoldenCase[]> {
    // 按意图分组，同意图的 Case 一起处理
    const byIntent = this.groupBy(errorCases, "intent");
    const goldenCases: GoldenCase[] = [];

    for (const [intent, cases] of Object.entries(byIntent)) {
      // 每个意图取 Top 3 高频错误 Case
      const topCases = cases.slice(0, 3);
      for (const c of topCases) {
        goldenCases.push(await this.convertToGoldenCase(c));
      }
    }

    return goldenCases;
  }

  /**
   * 评估 Case 难度
   * 为什么评估难度？
   * 不同难度的 Case 用于不同目的：
   * - Easy: 用于 Few-shot 示例
   * - Medium: 用于 Prompt 优化
   * - Hard: 用于微调训练数据
   */
  private assessDifficulty(errorCase: ErrorCase): "easy" | "medium" | "hard" {
    if (
      errorCase.context.turns === 1 &&
      errorCase.errorReason === "knowledge_gap"
    ) {
      return "easy"; // 单轮知识缺失，补充文档即可
    }
    if (
      errorCase.context.turns >= 3 ||
      errorCase.errorReason === "reasoning_error"
    ) {
      return "hard"; // 多轮推理错误，需要微调
    }
    return "medium";
  }
}

interface ErrorCase {
  id: string;
  userQuestion: string;
  agentAnswer: string;
  errorReason: string;
  intent: string;
  context: { turns: number };
  tags: string[];
}

interface GoldenCase {
  id: string;
  source: string;
  userQuestion: string;
  correctAnswer: string;
  reasoning: string;
  intent: string;
  difficulty: "easy" | "medium" | "hard";
  tags: string[];
  createdAt: Date;
  reviewed: boolean;
}
```

### 2.3 模型更新策略

**文件：`agent-platform/src/flywheel/model-updater.ts`**

```typescript
/**
 * 模型更新器
 *
 * 为什么有三种更新方式？
 * 不是所有优化都需要微调模型——微调最慢但最持久，
 * Prompt 更新最快但效果有限，需要根据场景选择
 */
export class ModelUpdater {
  /**
   * 更新策略选择
   *
   * @param goldenCases 本次新增的 Golden Case
   * @returns 推荐的更新策略
   */
  selectStrategy(goldenCases: GoldenCase[]): UpdateStrategy {
    const easyCount = goldenCases.filter((c) => c.difficulty === "easy").length;
    const hardCount = goldenCases.filter((c) => c.difficulty === "hard").length;

    if (hardCount > 10) {
      return "fine_tune"; // 困难 Case 多，微调效果最好
    }
    if (easyCount > 5) {
      return "few_shot"; // 简单 Case，补充 Few-shot 示例即可
    }
    return "prompt_update"; // 少量 Case，优化 Prompt 最快
  }

  /**
   * 执行 Prompt 更新
   * 为什么 Prompt 更新最快？
   * 不需要训练，改文本即可，灰度发布 30 分钟生效
   */
  async updatePrompt(goldenCases: GoldenCase[]): Promise<void> {
    const improvements = this.extractPromptImprovements(goldenCases);

    const newPrompt = await this.llm.generateOptimizedPrompt({
      currentPrompt: this.getCurrentPrompt(),
      improvements,
      goldenCases: goldenCases.slice(0, 3), // 只给 3 个示例，避免 Prompt 过长
    });

    await this.deployPrompt(newPrompt, { strategy: "canary", percent: 5 });
  }

  /**
   * 执行 Few-shot 更新
   * 为什么 Few-shot 比微调更适合小规模更新？
   * Few-shot 直接在 Prompt 中加示例，零成本、即时生效
   * 微调需要 GPU 训练，成本高、周期长
   */
  async updateFewShot(goldenCases: GoldenCase[]): Promise<void> {
    const examples = goldenCases
      .filter((c) => c.difficulty === "easy")
      .slice(0, 5) // 最多 5 个示例，避免上下文窗口溢出
      .map((c) => ({
        user: c.userQuestion,
        assistant: c.correctAnswer,
      }));

    await this.updateSystemPromptWithExamples(examples);
  }
}

type UpdateStrategy = "prompt_update" | "few_shot" | "fine_tune";
```

## 第三讲：差做法 vs 好做法

```
┌──────────────────────────────────────────────────────────────┐
│  ❌ 差的数据飞轮                                              │
│                                                              │
│  1. 只收集 👍/👎，不收集原因                                  │
│     → 知道"差"但不知道"为什么差"，无法优化                     │
│                                                              │
│  2. 反馈收集了，但没人分析                                     │
│     → 数据躺在数据库里吃灰，飞轮根本没转起来                   │
│                                                              │
│  3. 所有错误 Case 都人工标注 Golden Case                       │
│     → 标注成本高，一个 Case $5-10，1000 个就是 $5000-10000    │
│                                                              │
│  4. 直接全量上 Prompt 更新，不灰度                             │
│     → 新 Prompt 可能引入新问题，影响所有用户                    │
│                                                              │
│  ✅ 好的数据飞轮                                              │
│                                                              │
│  1. 显式+隐式反馈双通道收集                                    │
│     → 覆盖率从 5% 提升到 80%+，数据更全面                      │
│                                                              │
│  2. 每周自动化周报：Top 5 最差意图 + 趋势对比                  │
│     → 不需要人工分析，系统自动告诉你"该优化什么"               │
│                                                              │
│  3. LLM 生成 Golden Case + 人工审核                            │
│     → 标注成本降到 $0.5-1/条，效率提升 10 倍                   │
│                                                              │
│  4. 灰度发布验证：Prompt 更新 → 5% 灰度 → 观察 → 全量         │
│     → 有问题只影响 5% 用户，安全可控                           │
└──────────────────────────────────────────────────────────────┘
```

#### 选择题

**Q-C1.** 数据飞轮四步循环的正确顺序是什么？

- A. 收集反馈 → 分析问题 → 优化数据 → 更新模型 → 回到收集反馈
- B. 更新模型 → 收集反馈 → 分析问题 → 上线

## 2026年最新动态（截至2026年8月）

### Agent-in-the-Loop（AITL）数据飞轮

2026 年 AITL 范式成为 Agent 持续改进的标准方法：

**核心流程：**

1. Agent 执行任务，收集交互数据
2. 人类专家对 Agent 输出打分（标注）
3. 高质量标注数据用于微调模型
4. 微调后的模型部署回 Agent 中
5. Agent 性能提升 → 更多用户使用 → 更多数据 → 循环

### 飞轮驱动指标

| 阶段 | 指标           |   目标   |
| ---- | -------------- | :------: |
| 收集 | 日均交互量     |  > 1000  |
| 标注 | 标注一致性     |  > 90%   |
| 训练 | 模型准确率提升 | +2% / 月 |
| 部署 | 回滚率         |   < 5%   |

### 2026 年数据飞轮趋势

- EU AI Act 要求高风险 AI 系统记录训练数据来源
- 飞轮数据需满足合规审计要求
- LLM-as-Judge 自动标注技术成熟，标注成本从 $5-10/条 降至 $0.1-0.5/条
- 合成数据（Synthetic Data）在飞轮中占比从 20% 升至 60%+
