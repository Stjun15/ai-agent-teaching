## 概念讲解

---

### 第一讲：单 Agent 撑不起一个平台

#### 1.1 单 Agent 的三个卡点

当前 agent-platform（v1.0）是单 Agent：

```
用户请求 → POST /api/chat → 单一 AgentRuntime → 返回结果
```

如果平台要同时服务 MBTI 测评和编程面试，单 Agent 会卡在三个地方：

| 卡点           | 表现                                                      | 后果                             |
| :------------- | :-------------------------------------------------------- | :------------------------------- |
| **业务混杂**   | 一个 Agent 既要懂 MBTI 又要懂面试，system prompt 越写越长 | 意图互相干扰，回答质量下降       |
| **配置混杂**   | 所有 Agent 配置硬编码在 bootstrap 里                      | 换业务必须改代码，违背"零改内核" |
| **跨切面散落** | 成本追踪、Trace 记录散落在各处                            | 无法统一拦截、统一治理           |

> **类比：** 单 Agent 像"一个全科医生包打天下"。病人多了、科室多了，全科医生就撑不住了——你需要**前台分诊（Captain）+ 各科室专家（Worker）**。

#### 1.2 一句话记住痛点

> **单 Agent 是"一个模型 + 一套配置"服务所有业务；多 Agent 是"一个入口 + 多个专家"各管一摊。** 平台要通用，就必须从"单"走向"多"。

---

### 第二讲：Captain/Worker 模式

#### 2.1 架构总览

```
用户请求 → POST /api/chat
              │
              ▼
    ┌─────────────────────┐
    │   Captain Agent     │  ← 意图分析 + 任务分发（前台分诊）
    └──────┬──────────────┘
           │ 事件: agent:dispatch
           ▼
    ┌─────────────────────┐
    │      事件总线        │  ← 跨切面拦截（广播系统）
    └──────┬──────────────┘
           ▼
    ┌──────────────┐    ┌──────────────┐
    │ MBTI Worker  │    │Interview     │
    │  Agent       │    │Worker Agent  │
    └──────┬───────┘    └──────┬───────┘
           │ MCP               │ MCP
           ▼                   ▼
    mbti-mcp-server    interview-mcp-server
```

#### 2.2 Captain 的职责边界

**Captain 只做两件事：意图分析 + 任务分发，不做任何具体业务逻辑。**

- 用户说"我想测 MBTI" → 分发给 MBTI Worker
- 用户说"帮我准备算法面试" → 分发给 Interview Worker
- 用户闲聊 → 直接回复，介绍平台能力
- 无法确定 → 反问用户

> **关键：** Captain 用**小模型**（意图分析简单）+ **低温度**（保证路由一致性）+ **唯一工具** `dispatch_to_worker`。它越"笨"越"死板"越好——路由要的是稳定，不是创意。

#### 2.3 Worker 的职责

每个 Worker 是**独立的 AgentRuntime 实例**，拥有自己的：

- **Profile**（用什么模型/工具/沙箱/记忆）
- **Preset**（怎么跑循环/几步/超时/是否 HITL）
- **独立 Memory 命名空间**（`mbti:{userId}` / `interview:{userId}`，互不串）

> **类比：** Captain 是前台接待员，只问"您看哪个科？"然后带路。Worker 是各科室专家，接待员绝不替专家看病。

---

### 第三讲：Profile/Preset 双层配置

这是"换业务零改内核"的**工程落点**。

#### 3.1 为什么拆两层

| 层          | 管什么 | 一句话                                         |
| :---------- | :----- | :--------------------------------------------- |
| **Profile** | 用什么 | 模型、工具白名单、沙箱、记忆命名空间           |
| **Preset**  | 怎么用 | 循环模式、步数、超时、HITL、system prompt 模板 |

> **为什么要拆？** 因为"用什么"和"怎么用"是**两个独立变化的维度**。同一个模型（Profile）可以配不同的循环策略（Preset）；同一个循环策略可以服务不同的业务。拆开才能自由组合。

#### 3.2 两个 Worker 的配置差异（对比记忆）

| 维度 | MBTI Worker                                    | Interview Worker                                                                          |
| :--- | :--------------------------------------------- | :---------------------------------------------------------------------------------------- |
| 模型 | 小模型（测评简单）                             | 大模型（面试复杂）                                                                        |
| 工具 | `mbti_judge` / `mbti_question` / `mbti_lookup` | `interview_plan` / `generate_question` / `run_code` / `evaluate_answer` / `submit_report` |
| 沙箱 | `none`                                         | `judge0`（要跑代码）                                                                      |
| 循环 | ReAct                                          | Plan-and-Execute                                                                          |
| HITL | `false`                                        | `true`（出报告要审批）                                                                    |

> **洞察：** 两个 Worker 的差异**全部体现在配置里，不体现在代码里**。这就是"换业务 = 换配置"的含义——加一个业务，就是加一个 Profile + Preset + 一个 MCP Server，内核一行不改。

#### 3.3 工具白名单为什么重要

MBTI Worker 的 `tools` 白名单只含 `mbti_*`，**它物理上无法调用 interview 的工具**。这是"隔离"在配置层的体现——不是靠"开发者记得不越权"，而是靠"白名单结构上就不给权限"。

---

### 第四讲：事件总线——跨切面拦截

多 Agent 之后，每个 Agent 都会产生工具调用、HITL 审批、Agent 切换等事件。如果每个 Agent 自己处理，代码就重复了。**事件总线把它们统一拦截。**

| 事件             | 拦截点     | 干什么                |
| :--------------- | :--------- | :-------------------- |
| `tool:before`    | 工具调用前 | 参数校验 + 成本预估   |
| `tool:after`     | 工具调用后 | 结果校验 + Trace 记录 |
| `tool:error`     | 工具报错   | 错误记录 + 告警       |
| `hitl:required`  | 需审批     | 注册审批（挂起）      |
| `agent:switch`   | Agent 切换 | 上下文切换 + 日志     |
| `agent:complete` | Agent 完成 | 执行统计 + 成本核算   |

> **类比：** 事件总线像医院的**广播系统**——每个科室（Worker）不用自己装监控，全院统一广播"谁在做什么、花了多少钱、有没有出错"。成本追踪、Trace、审批这些**跨切面关注点**，一次注册，处处生效。

**设计要点：**

- 异步处理，不阻塞 Agent 主流程
- 一个 handler 抛错不影响其他（异常隔离）
- 支持动态注册/注销

---

### 第五讲：降级策略与内核零改动

#### 5.1 降级：Captain 挂了怎么办

Captain 是意图分析，它可能超时或返回异常。降级策略：

```
Captain 意图分发失败
    ↓
自动降级为 URL 路由
    ↓
/api/chat/mbti  → 直接创建 MBTI Worker，跳过 Captain
/api/chat/interview → 直接创建 Interview Worker，跳过 Captain
```

响应里标记 `"routing": "fallback"`，方便监控排查。

> **关键：** 降级**不打折**——Worker 的完整 Agent Loop 照常运行，只是跳过了 Captain 的意图分析。用户只是少了个"自动分诊"，功能一个不少。

#### 5.2 平台内核零改动（红线）

多 Agent 路由的**铁律**：`agent.ts`、`tool.ts`、`mcp/client.ts`、`memory.ts`、`approval.ts`、`trace.ts`、`cost.ts` **一律不改**。新增能力全部通过**新增文件 + bootstrap 装配**实现：

```
新增文件：
  agent-teams.ts   ← Captain/Worker 团队
  profile.ts       ← Profile/Preset 加载
  event-bus.ts     ← 事件总线（若未存在）
bootstrap.ts       ← 装配（唯一允许改的入口）
```

> **为什么是红线？** 因为"内核零改动"是整个平台的**核心卖点**——换业务零改内核。如果做多 Agent 要改内核，那这个卖点就崩了。多 Agent 本身也是"平台能力"，必须遵守同样的规则。
