## 为什么需要上下文工程？

> **场景：** 用户和客服 Agent 聊了 50 轮，从订单查询到退货政策到物流投诉。第 51 轮用户问"那个订单到哪了？"——Agent 回复："请问您的订单号是？"用户怒了："我第 3 轮就告诉你了！ORDER123！"——Agent 不是故意忘记，而是上下文窗口只有 128K，第 3 轮的消息早被截断了。

上下文工程就是管理"LLM 一次能看多少信息"的学问。GPT-5.6 虽然支持 1.05M token 上下文，但**塞得越多越贵、越慢、越容易分心**。上下文工程的目标不是"塞更多"，而是**"只塞最重要的"**。

### 类比：考试时的"开卷资料" v.s. 上下文工程

```
┌──────────────────────────────────────────────────────────────────┐
│  考试开卷                        Agent 上下文工程                  │
│  ────────                        ──────────────                  │
│  带了一堆书，但考试只能翻几页    System Prompt + 工具 + 历史       │
│                                 塞太多 → 找不到重点               │
│                                                                  │
│  策略1：只带重点笔记（摘要）     → 摘要压缩：把历史对话压缩成摘要   │
│  策略2：翻到哪页看哪页（滑动）   → 滑动窗口：只保留最近 N 条       │
│  策略3：标记重点章节（优先级）   → 智能裁剪：重要信息高优先级保留   │
│  策略4：分科目装订（分层）       → 分层注入：不同信息不同生命周期   │
│                                                                  │
│  核心认知：开卷考的关键不是带多少书，而是快速找到答案的那一页       │
└──────────────────────────────────────────────────────────────────┘
```

### 差做法 vs 好做法

| 差做法 ❌                             | 好做法 ✅                                      |
| ------------------------------------- | ---------------------------------------------- |
| 所有历史消息全塞进上下文，超了就报错  | 滑动窗口 + 摘要压缩，动态管理 Token 预算       |
| 重要的 System Prompt 和工具定义被截断 | 分层注入：System Prompt 常驻，RAG 结果按需注入 |
| 工具返回的大段数据原样保留            | 工具结果截断/摘要，只保留关键信息              |
| 用户 10 轮前说的订单号被丢弃          | 关键实体提取 + 状态层持久化（如"当前订单号"）  |
| 所有信息同等优先级，重要信息被挤掉    | 智能裁剪：含订单号/金额的消息高优先级保留      |

### 第一讲：上下文窗口的挑战

#### 1.1 上下文窗口限制

```
各模型的上下文窗口：
  GPT-4o-mini: 128K tokens（约 10 万汉字）
  GPT-4o: 128K tokens
  DeepSeek-V3: 128K tokens
  Claude 3.5 Sonnet: 200K tokens

看起来很大？但实际上：
  - System Prompt: 500 tokens
  - 工具 Schema: 300 tokens
  - 工具调用结果: 200-500 tokens/次
  - 用户消息: 50-200 tokens/条
  - 模型回复: 100-500 tokens/条

一次典型的 Agent 对话（5轮 ReAct）：
  System + 工具定义 + 5×(用户+模型+工具调用+工具结果)
  ≈ 500 + 300 + 5×800 = 4800 tokens

50轮的对话：
  ≈ 500 + 300 + 50×800 = 40,800 tokens

看起来还没超？但加上 RAG 检索的文档（可能几千 tokens），
加上多轮工具调用的结果，很容易超出窗口。
```

#### 1.2 超出窗口的后果

```
超出上下文窗口后：
  - 最早的对话被截断 → Agent "失忆"
  - 重要的 System Prompt 可能被截断 → Agent "变傻"
  - 工具调用结果被截断 → Agent 拿到不完整信息
  - API 直接报错 → 对话中断
```

### 第二讲：四种上下文管理策略

#### 2.1 策略1：滑动窗口

```
原理：只保留最近的 N 条消息，丢弃旧的

实现：
  messages = [system_prompt] + messages[-N:]

优点：简单，不会丢失最近的上下文
缺点：可能丢失重要信息（如用户10轮前说的订单号）

适用场景：对话不需要长期记忆的简单场景
```

```python
def sliding_window(messages: list, max_tokens: int = 8000) -> list:
    """滑动窗口：保留 System Prompt + 最近的消息"""
    system_prompt = messages[0]  # 保留 System Prompt

    # 从后往前取，直到接近 token 限制
    selected = []
    current_tokens = count_tokens(system_prompt)

    for msg in reversed(messages[1:]):
        msg_tokens = count_tokens(msg)
        if current_tokens + msg_tokens > max_tokens:
            break
        selected.insert(0, msg)
        current_tokens += msg_tokens

    return [system_prompt] + selected
```

#### 2.2 策略2：摘要压缩

```
原理：用 LLM 对历史对话做摘要，只保留摘要

实现：
  if len(messages) > 20:
      # 对前10条消息做摘要
      summary = llm.summarize(messages[1:11])
      # 替换为摘要
      messages = [system_prompt, summary_message] + messages[11:]

优点：保留历史信息的"精华"
缺点：摘要可能丢失细节，且多一次 LLM 调用

适用场景：需要保留长期对话概况的场景
```

```python
def summarize_history(messages: list, threshold: int = 20) -> list:
    """对超过阈值的消息做摘要"""
    if len(messages) <= threshold:
        return messages

    # 对前一半消息做摘要
    old_messages = messages[1:threshold//2]
    recent_messages = messages[threshold//2:]

    summary = llm.chat.completions.create(
        model="glm-4.7-flash",
        messages=[{
            "role": "user",
            "content": f"请用100字以内总结以下对话的关键信息：\n{old_messages}"
        }]
    ).choices[0].message.content

    return [messages[0]] + [{"role": "system", "content": f"历史对话摘要：{summary}"}] + recent_messages
```

#### 2.3 策略3：智能裁剪

```
原理：根据重要性决定保留哪些消息

重要性判断：
  - 包含订单号、金额等关键信息 → 高优先级
  - 工具调用结果 → 中优先级
  - 闲聊、问候 → 低优先级
  - 重复内容 → 可丢弃

实现：
  for msg in messages:
      score = calculate_importance(msg)
      if score > threshold:
          keep(msg)
```

#### 2.4 策略4：分层注入

```
原理：不同信息放在不同"层"，按需注入

三层结构：
  第1层（常驻）：System Prompt + 工具定义
    → 始终在上下文窗口中

  第2层（按需注入）：RAG 检索结果、用户画像
    → 只在需要时注入，用完移除

  第3层（动态）：对话历史、工具调用结果
    → 动态管理，超出窗口时压缩或丢弃
```

### 第三讲：TypeScript 实现——上下文管理器

#### 3.1 ContextManager：统一上下文管理

```typescript
// agent-platform/src/context/context-manager.ts
// 统一上下文管理：Token 预算分配 + 四种策略协同

import OpenAI from "openai";

interface Message {
  role: "system" | "user" | "assistant" | "tool";
  content: string;
  toolCalls?: { name: string; arguments: string }[];
}

export class ContextManager {
  private openai: OpenAI;
  // Token 预算分配（2026年 GPT-5.6 系列，总预算 128K tokens）
  private readonly TOKEN_BUDGET = {
    systemPrompt: 3000, // System Prompt 预留
    toolDefinitions: 2000, // 工具定义预留
    ragResults: 5000, // RAG 检索结果预留
    history: 100000, // 对话历史上限
    safety: 18000, // 安全余量
  };

  constructor() {
    this.openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
  }

  // 策略1：滑动窗口 — 保留最近 N 条消息
  slidingWindow(messages: Message[], maxTokens: number = 8000): Message[] {
    const systemPrompt = messages[0]; // 保留 System Prompt
    const selected: Message[] = [];
    let currentTokens = this.estimateTokens(systemPrompt.content);

    // 从后往前取，直到接近 token 限制
    for (let i = messages.length - 1; i >= 1; i--) {
      const msgTokens = this.estimateTokens(messages[i].content);
      if (currentTokens + msgTokens > maxTokens) break;
      selected.unshift(messages[i]);
      currentTokens += msgTokens;
    }

    return [systemPrompt, ...selected];
  }

  // 策略2：摘要压缩 — 用 LLM 对历史消息做摘要
  async summarizeHistory(
    messages: Message[],
    threshold: number = 20,
  ): Promise<Message[]> {
    if (messages.length <= threshold) return messages;

    const oldMessages = messages.slice(1, Math.floor(threshold / 2));
    const recentMessages = messages.slice(Math.floor(threshold / 2));

    const response = await this.openai.chat.completions.create({
      model: "gpt-5.6-mini", // 2026年：用 mini 做摘要，性价比最高
      messages: [
        {
          role: "user",
          content: `请用100字以内总结以下对话的关键信息（订单号、金额、用户需求等）：\n${oldMessages.map((m) => m.content).join("\n")}`,
        },
      ],
      max_tokens: 200,
      temperature: 0.1,
    });

    const summary = response.choices[0].message.content || "";
    return [
      messages[0], // System Prompt
      { role: "system", content: `历史对话摘要：${summary}` },
      ...recentMessages,
    ];
  }

  // 策略3：智能裁剪 — 按重要性保留消息
  smartTruncate(messages: Message[], maxTokens: number = 8000): Message[] {
    // 给每条消息打分
    const scored = messages.slice(1).map((msg) => ({
      message: msg,
      score: this.calculateImportance(msg),
    }));

    // 按分数降序排列
    scored.sort((a, b) => b.score - a.score);

    // 从高分到低分选取，直到接近 token 限制
    const systemPrompt = messages[0];
    let currentTokens = this.estimateTokens(systemPrompt.content);
    const selected: Message[] = [];

    for (const { message } of scored) {
      const msgTokens = this.estimateTokens(message.content);
      if (currentTokens + msgTokens > maxTokens) break;
      selected.push(message);
      currentTokens += msgTokens;
    }

    // 按原始顺序排序（保证对话顺序）
    selected.sort((a, b) => messages.indexOf(a) - messages.indexOf(b));

    return [systemPrompt, ...selected];
  }

  // 策略4：分层注入 — 不同信息不同生命周期
  buildLayeredContext(
    systemPrompt: string,
    toolDefinitions: string,
    history: Message[],
    ragResults?: string,
    userProfile?: string,
  ): Message[] {
    const context: Message[] = [];

    // 第1层（常驻）：System Prompt + 工具定义
    context.push({
      role: "system",
      content: `${systemPrompt}\n\n可用工具：\n${toolDefinitions}`,
    });

    // 第2层（按需注入）：用户画像 + RAG 结果
    if (userProfile) {
      context.push({
        role: "system",
        content: `当前用户画像：${userProfile}`,
      });
    }
    if (ragResults) {
      context.push({
        role: "system",
        content: `相关知识库检索结果：${ragResults}`,
      });
    }

    // 第3层（动态）：对话历史
    context.push(...history);

    return context;
  }

  // 工具结果截断 — Agent 场景专属策略
  truncateToolResult(result: string, maxLength: number = 2000): string {
    if (result.length <= maxLength) return result;
    return (
      result.slice(0, maxLength) +
      `\n...(结果过长，已截断，共 ${result.length} 字符)`
    );
  }

  // 工具结果摘要 — Agent 场景专属策略
  async summarizeToolResult(
    result: string,
    maxTokens: number = 500,
  ): Promise<string> {
    if (result.length < 1000) return result;

    const response = await this.openai.chat.completions.create({
      model: "gpt-5.6-mini",
      messages: [
        { role: "system", content: "请用简洁的语言总结以下数据的关键信息：" },
        { role: "user", content: result },
      ],
      max_tokens: maxTokens,
    });

    return response.choices[0].message.content || result;
  }

  // 重要性打分（智能裁剪的核心）
  private calculateImportance(message: Message): number {
    let score = 0;
    const content = message.content;

    // 包含关键实体（订单号、金额、日期）→ 高优先级
    if (/ORDER\d+/i.test(content)) score += 30;
    if (/\d+元|\$\d+/.test(content)) score += 20;
    if (/\d{4}-\d{2}-\d{2}/.test(content)) score += 10;

    // 用户消息权重更高
    if (message.role === "user") score += 15;
    if (message.role === "system") score += 50; // System Prompt 最高优先级

    // 闲聊/问候 → 低优先级
    if (/你好|谢谢|再见|哈哈/.test(content)) score -= 10;

    return score;
  }

  // 估算 token 数量（简化版，1 token ≈ 0.75 中文字符）
  private estimateTokens(text: string): number {
    return Math.ceil(text.length * 0.75);
  }
}
```

### 第四讲：Agent 场景的上下文管理

> 来自 AI 应用开发的核心洞察：Agent 的 messages 增长速度远快于普通对话，因为每次工具调用都会增加至少 2 条消息。

#### 4.1 Agent 对话的特殊性

```
普通对话的 messages：
  user → assistant → user → assistant → ...

Agent 的 messages：
  user → assistant(tool_call) → tool(结果) → assistant(tool_call) → tool(结果) → ... → assistant(最终回答)
```

如果工具返回了一个大文件内容或大量数据库查询结果，Token 会爆炸式增长。

#### 4.2 策略：工具结果截断

```python
def execute_tool(tool_call):
    result = run_tool(tool_call)

    MAX_RESULT_LENGTH = 2000
    if len(result) > MAX_RESULT_LENGTH:
        result = result[:MAX_RESULT_LENGTH] + f"\n...(结果过长，已截断，共 {len(result)} 字符)"

    return result
```

#### 4.3 策略：工具结果摘要

让 AI 先总结工具返回的大量数据，再继续推理：

```python
def summarize_tool_result(result, max_tokens=500):
```

#### 4.4 策略：历史消息压缩

当 messages 太长时，把早期对话压缩成摘要：

```python
def compress_history(messages, max_messages=20):
    if len(messages) <= max_messages:
        return messages

    system_msg = messages[0]
    old_messages = messages[1:-max_messages]   # 要压缩的旧消息
    recent_messages = messages[-max_messages:]  # 保留的近期消息

    summary = summarize_messages(old_messages)

    return [
        system_msg,
        {"role": "system", "content": f"之前的对话摘要：{summary}"},
    ] + recent_messages
```

> **核心原则**：Agent 场景下，上下文管理 = 通用策略（滑动窗口/摘要压缩）+ Agent 专属策略（工具结果截断/工具结果摘要/历史压缩）。

**① 场景**：上下文工程的核心挑战是 LLM 上下文窗口有限，但 Agent 对话消息增长极快——每轮 ReAct 至少增加 2 条消息（tool_call + tool_result）。当对话超过 20 轮，就需要**摘要压缩 prompt** 把历史对话压成摘要。这个 prompt 的难点在于"压缩后不能丢失关键信息"——订单号、金额、商品名、用户决策点必须保留，否则 Agent 会"失忆"。

**② 六要素对照表**：

| 要素     | 摘要压缩 prompt 填什么                                                                                                                                                                             |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 角色     | 对话摘要生成器（只压缩，不推理，不评价）                                                                                                                                                           |
| 任务     | 将以下对话历史压缩为 ≤150 字的摘要，用于后续对话的上下文注入                                                                                                                                       |
| 上下文   | 完整对话历史（含用户消息、AI 回复、工具调用名称及结果）                                                                                                                                            |
| 约束     | ① 必须保留：订单号（ORDERxxx）、金额、商品名、用户明确决策（"我要退货"）；② 必须丢弃：闲聊/问候（"你好""谢谢"）、工具调用中间结果超过 200 字的只保留结论；③ 不编造对话中没有的信息；④ 输出 ≤150 字 |
| 参考     | 当前对话主题（用于判断哪些信息是"关键"的——如退货主题下"退货条件"比"物流信息"更关键）                                                                                                               |
| 输出格式 | 纯文本摘要，≤150 字                                                                                                                                                                                |

**③ 示例 Prompt**（摘要压缩，可直接用）：

```
你是对话摘要生成器。将以下对话历史压缩为简短摘要，供后续对话使用。

必须保留的信息：
- 订单号（如 ORDER123）、金额、商品名
- 用户明确表达的需求或决策（如"我要退货""帮我查物流"）
- 工具调用结论（如"查询结果：订单已发货，可退货"）

必须丢弃的信息：
- 闲聊/问候（"你好""谢谢""在吗"）
- 工具调用完整原始数据（超过 200 字的只保留一句结论）
- 重复内容

不要编造对话中没有的信息。输出 ≤150 字。

对话历史：{history}

摘要：
```

**④ 反例 + 为什么**：

```
摘要压缩 prompt：'把对话总结一下。'   // ❌
```

错在哪：① 没锁"必须保留"——LLM 压缩时可能把"订单 ORDER123 金额 299 元"压缩成"用户查了订单"，丢失 ORDER123 和 299 这两个下游 Agent 必需的信息；② 没锁丢弃范围——工具返回的 2000 字 JSON 被原样保留，摘要比原文还长，失去压缩意义；③ 没锁字数——LLM 可能输出 500 字摘要，注入上下文后反而占更多 Token。

**⑤ 完成标准**：能独立写出包含**必须保留关键实体 / 必须丢弃闲聊和工具原始数据 / 不编造信息 / 输出字数限制**四条款的摘要压缩 prompt。

**Q-C1.** 对话超出上下文窗口后，最先表现为？

B. 最早的对话被截断，Agent 开始"失忆"、重要 System Prompt 可能被截断

D. 没有任何影响

> 答案：B。超出后最早的对话被截断，重要信息丢失导致"失忆"。

**Q-C2.** 滑动窗口策略的主要缺点是？
A. 实现过于复杂，难以编码
B. 可能丢失重要旧信息（如用户 10 轮前提到的订单号）
C. 每次都要多一次 LLM 调用
D. 无法保留 System Prompt

> 答案：B。滑动窗口只保留最近 N 条，旧的但重要的信息可能丢失。

**Q-C3.** 摘要压缩策略的缺点是？
A. 实现简单但没效果
B. 摘要可能丢失细节，且多一次 LLM 调用
C. 完全丢弃所有历史
D. 只保留 System Prompt

> 答案：B。摘要压缩保留历史"精华"，但可能丢细节且多一次 LLM 调用。

**Q-C4.** 在智能裁剪的重要性判断中，哪类信息应判为高优先级保留？
A. 闲聊、问候语
B. 包含订单号、金额等关键实体
C. 重复的客套话
D. 空消息

> 答案：B。含订单号、金额等关键信息应高优先级保留，闲聊可丢弃。

**Q-C5.** 分层注入中，哪一层信息常驻上下文窗口、始终保留？
A. RAG 检索结果
B. 用户画像
C. System Prompt + 工具定义
D. 全部历史对话

> 答案：C。第 1 层（System Prompt + 工具定义）常驻；第 2 层按需注入，第 3 层动态管理。

#### 场景分析题

**Q-S1.** 用户在对话第 3 轮说了"订单号 ORDER123"，第 50 轮问"我的订单到哪了？"，Agent 用滑动窗口却忘了订单号。请分析根因，并给出至少两种能解决该问题的策略。

> 根因：滑动窗口只保留最近 N 条，ORDER123 在第 3 轮早已被丢弃。方案：① 摘要压缩——把早期关键实体验证进摘要；② 智能裁剪——按重要性（含订单号的轮次高优先级）保留关键消息；③ 引入状态层（如 ConversationContext 的 state 持久保存"当前订单号"）。

**Q-S2.** HMall 客服对话已 50 轮，此时 RAG 又要注入几千 token 的文档，即将超出窗口。请设计一个分层注入方案控制 Token 用量。

## 2026年最新动态（截至2026年8月）

### GPT-5.6 系列上下文窗口一览

| 模型          |  上下文窗口  | 每百万 token 输入价格 | 适用场景                   |
| ------------- | :----------: | :-------------------: | -------------------------- |
| GPT-5.6-sol   | 1.05M tokens |         $1.25         | 长文档分析、Agent 复杂任务 |
| GPT-5.6-mini  | 1.05M tokens |        $0.075         | 摘要压缩、轻量级 Agent     |
| GPT-5.6-flash | 1.05M tokens |        $0.025         | 实时上下文处理             |

**2026 年核心变化：** 1.05M token 上下文窗口已成为标配，但"塞更多"不是解决方案——需更精细的上下文管理策略。

### 上下文工程 = 六大优化方向（2026 年）

| 方向           | 说明             | 2026 最佳实践               |
| -------------- | ---------------- | --------------------------- |
| 上下文窗口管理 | 控制 Token 预算  | 滑动窗口 + 摘要压缩         |
| 上下文压缩     | 减少不必要信息   | LLM 摘要 + 关键实体提取     |
| 上下文注入     | 动态插入相关信息 | RAG 结果按需注入            |
| 上下文优先级   | 重要信息靠前     | 含订单号/金额的消息高优先级 |
| 上下文结构化   | 格式规范化       | XML/JSON 结构化输出         |
| 上下文缓存     | 减少重复计算     | 相同 System Prompt 缓存复用 |

### 2026 年三阶段上下文管理策略

```
阶段1：上下文压缩（Context Compression）
  → 对话超过 20 轮 → 对前 10 轮做摘要
  → 摘要用 gpt-5.6-mini，成本 $0.075/百万 token

阶段2：上下文注入（Context Injection）
  → 每次 LLM 调用前，从 Memory 系统加载用户画像
  → 从 RAG 系统检索相关知识
  → 注入到 System Prompt 中

阶段3：上下文缓存（Context Caching）
  → System Prompt 和工具定义不变 → 缓存
  → 2026年：GPT-5.6 支持 Prompt Caching，缓存命中成本减半
```

### 四种策略的适用场景（2026 年共识）

| 策略     | 适用场景               | 风险           |
| -------- | ---------------------- | -------------- |
| 滑动窗口 | 实时对话、流式输出     | 旧信息完全丢失 |
| 摘要压缩 | 长对话归档、客服记录   | 细节丢失       |
| 智能裁剪 | 工具调用历史、中间推理 | 需额外索引系统 |
| 分层注入 | 企业知识库、多轮对话   | 设计复杂度高   |

### Token 预算管理（2026 年新话题）

- System Prompt 预分配 Token 预算（建议 3000-5000 tokens）
- 工具调用结果截断策略（单次结果不超过 2000 字符）
- 对话历史记忆衰减算法（越旧的消息权重越低）

### 2026 关键认知：上下文不是越大越好

> 1.05M token 上下文窗口不是让你把所有东西都塞进去。研究表明，LLM 对**中间位置**的信息注意力最差（"Lost in the Middle"效应）。真正重要的信息应该放在**开头（System Prompt）**或**结尾（最新消息）**。
>
> 上下文工程的核心是**信息密度**，不是信息量。

## 判断力日志：上下文工程四策略的取舍

### 问题

你在设计 Agent 的上下文管理方案时面临的核心矛盾：GPT-5.6 支持 1.05M token 上下文窗口，但"塞得越多越贵、越慢、越容易分心"。Agent 对话每轮 ReAct 至少增加 2 条消息（tool_call + tool_result），50 轮对话轻松突破 40K tokens。你需要在"不丢关键信息"和"控制 Token 成本"之间找到平衡点。

### 决策

我选择了**四种策略协同**而不是单一策略：

- **分层注入**作为骨架：第 1 层常驻 System Prompt + 工具定义（永不丢失），第 2 层按需注入 RAG 结果和用户画像（用完即移除），第 3 层动态管理对话历史
- **滑动窗口**作为兜底：保留最近 N 条消息 + System Prompt，防止 Token 硬超限
- **摘要压缩**作为长对话补充：超过 20 轮时对前半对话做摘要，保留关键实体（订单号/金额/商品名）
- **智能裁剪**作为 Agent 专属优化：工具结果截断（单次 ≤2000 字符），工具结果过大时先摘要再注入

### 取舍

- **滑动窗口**：实现最简单，但第 3 轮说的 ORDER123 在第 50 轮必定丢失 → 不适合需要长期记忆的场景
- **摘要压缩**：保留历史"精华"，但多一次 LLM 调用（gpt-5.6-mini，$0.075/百万 token），且摘要可能丢失细节（如"用户查了订单"丢掉了 ORDER123）
- **智能裁剪**：按重要性打分（含订单号 +30 分，闲聊 -10 分），精准但需要额外的打分逻辑和索引
- **分层注入**：设计复杂度最高，但结构最清晰——不同信息不同生命周期，常驻层永不丢失，按需层用完即弃
- **取舍结论**：分层注入定骨架 + 滑动窗口兜底 + 摘要压缩补长对话 + 智能裁剪降噪音，四者不是替代关系而是**分层协同**。单一策略无法覆盖所有场景。

### 防什么失败

- **防"对话太长，Agent 开始失忆"**：分层注入保证 System Prompt 和工具定义永不丢失，滑动窗口兜底防止 Token 硬超限报错
- **防"Token 费用爆炸"**：工具结果截断（≤2000 字符）+ 摘要压缩（长对话变摘要），避免无限制堆消息
- **防"重要信息被挤出上下文窗口"**：智能裁剪按重要性保留含订单号/金额的消息，闲聊/问候低优先级丢弃；Layer 2 的 RAG 结果用完即移除，不占用后续窗口
- **防"Lost in the Middle"效应**：重要信息放在 System Prompt（开头）或最新消息（结尾），不在中间位置埋关键信息
- **防"上下文工程和 Memory 系统混淆"**：上下文工程管"当前对话的工作台"，Memory 系统管"跨会话的档案柜"——新对话从 Memory 加载画像到上下文，结束时从上下文存入 Memory，边界清晰
