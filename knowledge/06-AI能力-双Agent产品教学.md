## 概念讲解

### 第一讲：为什么是两个 Agent？

#### 1.1 从问题出发

> "我已经有 agent-platform 了，能接 HMall、能接天机学堂，为什么还要做'双 Agent 产品'？这和之前有什么不同？"

**关键区别：** 之前接入 HMall/天机学堂，是**平台接业务服务**（MCP Server 暴露 REST 接口）。而双Agent产品是**平台接 AI Agent 产品**——每个产品本身就是一个会"思考、调用工具、多轮对话"的 Agent。

#### 1.2 一个不够，两个才行

| 场景                            | 能证明什么                         |
| ------------------------------- | ---------------------------------- |
| 做一个 Agent（如 MBTI）         | 只能证明"做了个产品"               |
| 做两个 Agent（MBTI + 面试教练） | 证明"平台是通用的、业务是可插拔的" |

**核心命题：** 同一个平台内核，**换业务不改一行代码**。一个 Agent 可能只是特例，两个差异巨大的 Agent 才能证明通用性。

#### 1.3 两个 Agent 故意选得差异极大

| 维度       | MBTI 职业规划师  | AI 编程面试教练           |
| ---------- | ---------------- | ------------------------- |
| 交互模式   | 问答式测评       | 代码编写+运行+评审        |
| MCP 工具数 | 3                | 5                         |
| 知识源     | 结构化 16 型数据 | RAG 编程知识库            |
| Memory     | 轻度（测评结果） | 重度（薄弱点+进步曲线）   |
| 安全敏感度 | 低（无代码执行） | 高（代码沙箱隔离）        |
| 成本模型   | 低（短对话）     | 高（代码运行+RAG+长对话） |

**综合差异度 4.3/5**——两个产品在交互、安全、成本、知识源上都不同，如果同一个内核能同时支撑它们，通用性就坐实了。

> **一句话：** 两个 Agent 不是"多做一倍的活"，而是"用第二个 Agent 证明平台的第一个 Agent 不是碰运气"。

**[确认理解]** 用自己的话讲：为什么一个 Agent 不够证明平台通用性？两个 Agent 在哪些维度上故意差异大？

### 第二讲：多 Agent 路由 —— 为什么用 Captain/Worker 而不是 URL 路由

#### 2.1 两种路由方案

**方案 A（v1.0 旧方案）：URL 路由**

```
POST /api/chat/mbti      → MBTI Agent
POST /api/chat/interview → Interview Agent
```

前端决定走哪个 Agent。**问题：** 用户要自己知道该访问哪个 URL；平台"零感知换业务"的卖点打折（前端要感知业务差异）。

**方案 B（v2.0 新方案）：Captain/Worker**

```
POST /api/chat → Captain Agent 意图分析 → 分发到 MBTI Worker 或 Interview Worker
```

**平台层决定**用户想干什么，自动分发。前端永远只调 `/api/chat`，不感知业务差异。

#### 2.2 Captain 是什么

Captain（船长）= 调度员。它**只做意图分析和任务分发，不做具体业务逻辑**。

```
用户说"帮我测测我的 MBTI" → Captain 判断 → 分发给 MBTI Worker
用户说"帮我准备算法面试"  → Captain 判断 → 分发给 Interview Worker
用户说"你好"              → Captain 直接回复，介绍平台能力
Captain 拿不准             → 询问用户想用哪个功能
```

Captain 唯一工具是 `dispatch_to_worker`：

```typescript
const dispatchTool = {
  name: "dispatch_to_worker",
  description: "将用户请求分发到指定的 Worker Agent",
  inputSchema: {
    type: "object",
    properties: {
      target: { type: "string", enum: ["mbti", "interview"] },
      context: {
        type: "string",
        description: "用户原始消息 + Captain 意图分析摘要",
      },
    },
    required: ["target", "context"],
  },
};
```

#### 2.3 降级策略

Captain 也会失败（LLM 超时）。降级为 URL 路由：

- `/api/chat/mbti` → 直接建 MBTI Worker，跳过 Captain
- 降级时响应带 `"routing": "fallback"` 标记，方便监控

> **一句话：** Captain 是"平台侧的大脑"，URL 路由是"脑子不转时的备用通道"。

### 第三讲：Profile 和 Preset —— "用什么"和"怎么用"分离（本文件重点）

#### 3.1 为什么会有两个概念

一个 Agent 有太多可配置项：用哪个模型、允许哪些工具、要不要沙箱、记忆空间、循环模式、最大步数、超时、要不要审批、系统提示词……

如果全塞进一个 `AgentConfig`，就混在一起了。任务书 v2.0 把它拆成两层：

| 层          | 回答的问题 | 包含                                                         |
| ----------- | ---------- | ------------------------------------------------------------ |
| **Profile** | **用什么** | model / tools / sandbox / memoryNamespace / temperature      |
| **Preset**  | **怎么用** | agentLoop / maxSteps / timeout / hitl / systemPromptTemplate |

#### 3.2 类比

- **Profile = 请什么人**：这个 Agent 用便宜的模型还是强的模型？允许碰哪些工具？要不要代码沙箱？
- **Preset = 怎么安排他干活**：用 ReAct 还是 Plan-and-Execute？最多干几步？超时多久？要不要领导审批？

#### 3.3 为什么必须分离

因为同一个 Agent 可以组合不同的 Profile 和 Preset：

```
MBTI：Profile(便宜模型, 3工具, 无沙箱) + Preset(ReAct, 15步, 无审批)
面试：Profile(强模型, 5工具, 沙箱)   + Preset(Plan-and-Execute, 20步, 有审批)
```

**更关键：** 换业务时，平台内核不动，**只换 Profile/Preset 配置**——这就是"换业务不改一行代码"在 Agent 配置层的体现。

#### 3.4 两个配置示例对比

| 配置               | MBTI Worker           | Interview Worker                 |
| ------------------ | --------------------- | -------------------------------- |
| model              | 便宜模型（测评简单）  | 强模型（评判需要）               |
| agentLoop          | ReAct（线性流程够用） | Plan-and-Execute（多阶段更合适） |
| maxSteps           | 15（4 维度 × 3-4 题） | 20（面试步骤更多）               |
| hitl               | false（测评不需审批） | true（面试报告要审批）           |
| contextWindowLimit | 8000                  | 16000                            |

> **注意：** 任务书里的 `gpt-4o-mini`/`gpt-4o` 是示例模型名，实际以平台环境变量配置为准（当前是智谱 GLM-4.7-Flash）。Profile 支持环境变量覆盖（如 `PROFILE_MBTI_MODEL`）。

### 第四讲：事件总线 —— 跨切面关注点统一拦截

#### 4.1 从问题出发

单 Agent 时代，Trace、成本记录、审批、日志这些"横切关注点"散落在各处。多 Agent 时代，Captain + 两个 Worker 各有各的工具调用——如果每个 Agent 自己记 Trace、自己记成本，代码重复，还容易漏。

**事件总线（EventBus）= 把所有横切关注点集中到一个地方拦截。**

#### 4.2 7 种事件

| 事件             | 触发时机         | 谁监听                      |
| ---------------- | ---------------- | --------------------------- |
| `agent:dispatch` | Captain 分发任务 | AgentTeams                  |
| `agent:switch`   | 切换 Agent       | 日志                        |
| `tool:before`    | 工具调用前       | Trace + 成本预估            |
| `tool:after`     | 工具调用后       | Trace + 实际成本 + 结果校验 |
| `tool:error`     | 工具调用失败     | 错误记录                    |
| `hitl:required`  | 需要人工审批     | 审批登记中心                |
| `agent:complete` | Agent 完成       | 记录步数+耗时               |

#### 4.3 类比

事件总线 = 公司的**审计部门**。不管哪个部门（Agent）办事（调工具），进出都要过审计登记（Trace + 成本）；涉及对外承诺（HITL）要审批。

#### 4.4 两个关键性质

1. **异步处理**：事件触发不阻塞主流程（Agent 照常干活，审计后台记）
2. **隔离失败**：一个事件处理器抛错，不影响其他处理器和主流程（审计挂了，业务照跑）

> **一句话：** 事件总线让"记录、审批、校验"这些事，从每个 Agent 的重复代码里抽出来，变成一次注册、处处生效。

**[确认理解]** 事件总线解决什么问题？`tool:before` 和 `tool:after` 各记录什么？"隔离失败"是什么意思，为什么重要？

### 第五讲：平台内核零改动 —— 验收红线

#### 5.1 哪些是"内核"（不许动）

```
agent-platform/src/
├── agent.ts      ← ReAct 循环 + 状态机 + maxSteps
├── tool.ts       ← 工具注册表
├── mcp/client.ts ← MCP 动态发现
├── memory.ts     ← 三层记忆
├── approval.ts   ← HITL 审批
├── trace.ts      ← Trace
├── cost.ts       ← 成本追踪
└── plugin.ts     ← 插件热插拔
```

#### 5.2 哪些是"允许动的"

```
├── bootstrap.ts  ← 装配（唯一允许改的现有文件）
└── 新增文件：
    ├── event-bus.ts   ← 事件总线
    ├── profile.ts     ← Profile/Preset
    ├── agent-teams.ts ← Captain/Worker 调度
    └── plugins/mbti/  ← MBTI 薄层插件
```

#### 5.3 为什么这是红线

**"换业务不改一行代码"是整个项目的核心卖点。** 如果接一个业务就要改 `agent.ts`，那平台就不是平台，是个"为特定业务定制的大函数"。验收标准 v2.0 第一条就是：**内核文件改动数 = 0**。

> **一句话：** 内核是"不动产"，bootstrap 是"装配车间"，新增文件是"新厂房"。不动产不许动，能力全靠新建和装配。
