## 为什么需要 Tools 设计方法论？

> **真实场景：** 某团队给 Agent 定义了 20 个工具，每个工具有 8-10 个参数。上线后 Agent 频繁调用错误工具、传错参数。用户说"帮我退货"，Agent 调了 4 个工具才完成——先查订单、再查退货政策、再判断条件、再创建退货单。每次调用都有概率出错，4 次调用下来成功率不到 60%。根本原因是工具设计不合理——粒度太细、参数太多、缺乏错误处理。

**工具设计的好坏，直接决定了 Agent 的可用性。** 工具是 Agent 的"手"，手不好用，脑子再好也没用。

**类比：瑞士军刀 vs 专用工具**

```
瑞士军刀（太粗粒度）：
  一个工具做所有事 → 模型不知道这个工具到底能做什么，不敢用

专用工具箱（太细粒度）：
  开瓶器、螺丝刀、剪刀... → 模型需要判断用哪个，每步都可能出错

合理的工具套装（合适粒度）：
  开瓶器（开瓶）、剪刀（剪东西）、螺丝刀（拧螺丝）
  一个工具对应一个明确的意图
```

## 核心概念

### 第一讲：工具粒度——一个工具做多少事？

```
┌──────────────────────────────────────────────────────────────┐
│              工具粒度决策树                                    │
│                                                              │
│  用户意图 → 可以拆成多个独立步骤？                             │
│     │                                                        │
│     ├── 不能 → 一个工具完成（如"查订单"）                      │
│     │                                                        │
│     └── 能 → 每个步骤是否独立有用？                            │
│           │                                                  │
│           ├── 是 → 拆成多个工具（如"查订单"+"创建退货"）       │
│           │                                                  │
│           └── 否 → 合并为一个工具（内部调多个API）             │
└──────────────────────────────────────────────────────────────┘
```

| 设计    | 示例                                                                   | 效果                          |
| ------- | ---------------------------------------------------------------------- | ----------------------------- |
| ❌ 太粗 | `do_everything(action="退货")`                                         | 模型不知道能做什么，不敢用    |
| ❌ 太细 | `get_status()` → `get_amount()` → `check_policy()` → `create_return()` | 4次调用，每次都可能出错       |
| ✅ 合适 | `query_order()` → `create_return()`                                    | 2次调用，每个对应一个用户意图 |

**黄金法则：一个工具 = 一个用户意图对应的操作。**

### 第二讲：工具参数设计

```python
# src/ai-service/tools/design_examples.py — 好参数 vs 坏参数

# ✅ 好参数设计：参数少而精，含义清晰
query_order_schema = {
    "name": "query_order",
    "description": "根据订单号查询订单详情",
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {
                "type": "string",
                "description": "订单号，格式如 ORDER123"
            }
        },
        "required": ["order_id"]
    }
}

# ❌ 坏参数设计：参数太多，模型容易传错
bad_schema = {
    "name": "query_order",
    "parameters": {
        "properties": {
            "order_id": {"type": "string"},
            "user_id": {"type": "string"},
            "start_date": {"type": "string"},
            "end_date": {"type": "string"},
            "status": {"type": "string"},
            "page": {"type": "integer"},
            "page_size": {"type": "integer"},
        }
    }
}
# 模型看到 7 个参数会懵，不知道该传哪个
```

**参数设计原则：**

- 必填参数：1-2 个（越少越好）
- 可选参数：不超过 3 个
- 总计：不超过 5 个参数
- 参数名要直观：`order_id` 而不是 `oid`
- description 要具体：不要"订单号"，要"订单号，格式如 ORDER123"

### 第三讲：工具返回值设计

```python
# src/ai-service/tools/return_design.py — 返回值设计

# ✅ 好返回值：人类可读 + 结构化 + 有建议
def query_order(order_id: str) -> str:
    order = db.find(order_id)
    if not order:
        return f"未找到订单 {order_id}。请确认订单号是否正确。"

    return f"""订单 {order_id} 详情：
- 状态：{order.status}
- 金额：¥{order.amount}
- 下单时间：{order.create_time}
- 商品：{order.items}
- 物流：{order.logistics_status}
- 是否可退货：{'是' if order.can_return else '否'}"""

# ❌ 坏返回值：原始 JSON，模型看不懂
def query_order_bad(order_id: str) -> str:
    return json.dumps(db.find(order_id))
    # {"id":123,"uid":456,"stat":2,"amt":29900,"ct":"2024-01-01"}
    # 模型需要自己"翻译" stat=2 是什么意思
```

**返回值原则：**

- ✅ 人类可读的文本（模型可以直接理解）
- ✅ 关键信息摘要（不要返回全部字段）
- ✅ 操作建议（"可退货"、"联系客服"）
- ❌ 原始 JSON（模型需要"翻译"）
- ❌ 数据库字段名（stat, uid, ct）
- ❌ 敏感信息（其他用户的订单、密码）

### 第四讲：错误处理与幂等性

```python
# src/ai-service/tools/error_handling.py — 错误处理 + 幂等性

def query_order(order_id: str) -> str:
    # 1. 参数校验
    if not order_id or not order_id.strip():
        return "错误：订单号不能为空"
    if not order_id.startswith("ORDER"):
        return "错误：订单号格式不正确，应以 ORDER 开头"

    # 2. 业务逻辑（带异常处理）
    try:
        order = db.find(order_id)
    except TimeoutError:
        return "查询超时，请稍后重试"
    except ConnectionError:
        return "服务暂时不可用，请稍后重试"

    # 3. 结果处理
    if not order:
        return f"未找到订单 {order_id}。请确认订单号是否正确。"
    return format_order(order)


# 幂等性：同一个操作执行多次，结果相同
# ✅ 幂等：query_order("ORDER123") 查10次，结果一样
# ❌ 非幂等：create_return("ORDER123") 调2次 → 创建了2个退货单！

# 非幂等操作的处理：
# 1. 加幂等键（idempotency_key）：客户端生成唯一ID，服务端去重
# 2. 状态检查：创建前检查是否已存在
# 3. HITL 审批：敏感操作需要人工确认
```

## 对比讲解：差做法 vs 好做法

| 维度     | ❌ 差做法                | ✅ 好做法                  |
| -------- | ------------------------ | -------------------------- |
| 粒度     | 一个工具做所有事         | 一个工具 = 一个用户意图    |
| 参数     | 7-10 个参数              | 必填 1-2 个，总计 ≤5 个    |
| 返回值   | 裸 JSON 或数据库字段     | 人类可读文本 + 摘要 + 建议 |
| 错误处理 | 直接抛异常               | 返回友好错误信息           |
| 幂等性   | 不处理，重复调用有副作用 | 幂等键 + 状态检查 + HITL   |

### 提示词教学：工具 description 怎么写才让 LLM 选对工具

> **AI：** 不重讲六要素模板（真源：`03-AI协作构建\03-AI协作构建技能.md`；进阶：`06-AI能力-Prompt工程实战.md`），只讲工具设计场景怎么填。

**① 场景**：工具设计的好坏，最终体现在 LLM 能不能"在正确的时候、选正确的工具、传正确的参数"。而 LLM 做这个决策的唯一依据就是**工具 Schema 的 description**——它是"给 LLM 看的接口文档"。工具粒度、参数设计、返回值设计的每个原则，最终都要翻译成 Schema 里的文字。

**② 六要素对照表**：

| 要素     | 工具 description 设计填什么                                                                                                                   |
| :------- | :-------------------------------------------------------------------------------------------------------------------------------------------- |
| 角色     | 工具名称（`name`），动词开头，清晰表达工具职责（如 `query_order`、`create_return`）                                                           |
| 任务     | `description` 字段，必须写清两件事：① 工具做什么；② **触发条件**——"当用户...时使用"                                                           |
| 上下文   | 参数 Schema（类型、格式、必填/可选）+ 工具间依赖（"需要先调用 X 获取 Y 后才能调用此工具"）                                                    |
| 约束     | ① 参数格式写死（如"订单号，格式如 ORDER123"）；② 返回值说明（"返回订单状态、金额，金额单位分"）；③ 幂等性声明（"此工具可重复调用，结果相同"） |
| 参考     | 工具实际执行逻辑（Feign 调哪个服务、数据库查哪个表）——写进 description 让 LLM 理解工具能力边界                                                |
| 输出格式 | 工具返回值的格式化模板（"订单 ORDER123：状态=已发货，金额=29900分"）                                                                          |

**③ 示例 Prompt**（工具 description 设计模板，可直接用）：

```
## 工具：query_order

【name】query_order

【description】根据订单号查询订单详情，包括订单状态、金额、商品列表、是否可退货。
当用户询问以下内容时使用此工具：
- 订单状态/进度（"我的订单到哪了""ORDER123 是什么状态"）
- 订单金额（"这个订单多少钱"）
- 购买记录（"我上次买了什么"）
- 退货条件（"这个能退吗"）

【parameters】
- order_id（string，必填）：订单号，格式如 ORDER123（ORDER + 3位数字）

【返回值】格式化字符串：'订单 {order_id}：状态={status}，金额={amount}分，是否可退货={can_return}'
- status：待支付 / 已支付 / 已发货 / 已完成 / 已取消
- amount：金额，单位"分"（前端自行转换）
- can_return：是 / 否（仅"已发货"且"7天内"为"是"）

【幂等性】此工具可重复调用，结果相同。
```

**④ 反例 + 为什么**：

```
工具 Schema：{
  "name": "qo",
  "description": "查订单",
  "parameters": {"oid": {"type": "string"}}
}   // ❌
```

错在哪：① name 缩写 `qo`——LLM 不知道这是什么，SSOT 不成立（Single Source of Truth）；② description 只有三个字——没有触发条件，LLM 不知道用户说"我上次买的那个"时该不该调；③ 参数名 `oid`——LLM 从用户消息中提取参数时，`oid` 和用户说的"订单号"语义不匹配，参数提取准确率下降；④ 没有返回值格式说明——LLM 拿到工具结果后不知道 `can_return` 字段的含义，可能错误解读。

**⑤ 完成标准**：能独立为工具写出包含**触发条件（"当用户...时使用"）/ 参数格式说明 / 返回值格式模板 / 幂等性声明**四条款的 Schema description。

## Quiz（闭卷）

> **AI：** 出 5 道题考下面内容，每题先批改，不通过进入补考。

1. **工具粒度**：用自己的话解释"一个工具 = 一个用户意图对应的操作"这条黄金法则。如果用户说"帮我查一下 ORDER123，能退的话帮我退了"，这个需求应该拆成几个工具？为什么？

2. **参数设计**：一个工具的参数设计，为什么"必填参数 1-2 个，总计不超过 5 个"？如果参数太多（如 7-10 个），LLM 在提取参数时会出什么问题？请举例说明。

3. **返回值设计**：工具返回值为什么不能直接返回原始 JSON 或数据库字段名？`{"stat":2,"amt":29900,"ct":"2024-01-01"}` 这个返回值给 LLM 后，LLM 会怎么解读？正确做法应该返回什么？

4. **幂等性**：`create_return("ORDER123")` 连续调用两次创建了两张退货单。请分析根因，并给出至少两种解决方案（不能只说"加幂等键"，要具体说明怎么加、加在哪）。

5. **跨讲串联**：从工具粒度 → 参数设计 → 返回值设计 → 错误处理与幂等性，这四个环节中，哪个环节设计不好对用户体验影响最大？为什么？请用一个具体场景说明。

**答案：**

1. 应拆成 2 个工具：query_order（查订单）和 create_return（创建退货）。因为"查订单"和"退货"是两个独立的用户意图，且 create_return 依赖 query_order 的结果（需要先确认可退）。如果合并为一个工具，LLM 无法处理"先查后判断"的逻辑。
2. 参数太多时 LLM 会：① 不知道该传哪个参数（如同时有 order_id 和 user_id，LLM 可能只传一个）；② 传错参数（如把 user_id 填到 order_id 里）；③ 漏传必填参数。例：7 个参数中有 start_date 和 end_date，用户说"查最近订单"，LLM 可能不传这两个参数导致返回全量数据。
3. LLM 解读：stat=2 不知道是什么状态，amt=29900 不知道是"分"还是"元"，ct="2024-01-01" 不知道是什么时间。LLM 会瞎猜或直接输出原始数据给用户。正确做法：`"订单 ORDER123：状态=已发货，金额=299.00元，下单时间=2024-01-01"`。
4. 根因：create_return 不是幂等操作，每次调用都创建新退货单。方案一：客户端生成幂等键（idempotency_key），服务端用 Redis 存储 `key → 退货单ID`，重复请求返回已有结果。方案二：创建前检查该订单是否已有"处理中"的退货单，有则返回已有退货单信息。
5. 返回值设计对用户体验影响最大。因为用户最终看到的是 LLM 基于工具返回值生成的自然语言回答。返回值是原始 JSON → LLM 解读错误 → 用户看到错误信息。场景：用户问"ORDER123 能退吗"，工具返回 `{"can_return": 0}`，LLM 解读为"不能退"，但实际 `can_return=0` 可能只是"未判断"。

2. **换一个场景**：你要给一个"外卖点餐"Agent 设计工具。请设计 3 个工具（search_restaurant、place_order、check_delivery），写出每个工具的 name、description（含触发条件）、parameters（含 required），并说明返回值应该包含什么、不应该包含什么。

**答案参考：**

2. search_restaurant：name="search_restaurant"，description="搜索附近餐厅，支持按菜系、评分筛选。当用户询问'附近有什么好吃的''推荐一家川菜馆'时使用"，parameters: {cuisine(可选), rating(可选)}，返回值含餐厅名/评分/距离/配送费，不含其他用户的订单记录。place_order：依赖 search_restaurant 的结果，需确认菜品和地址。check_delivery：查询配送进度，需订单号。
3. LLM 可能把所有订单信息都展示给用户，导致用户看到张三的订单详情——这是隐私泄露。这是工具设计的问题：工具应该只返回当前用户的订单，在查询时加 `WHERE user_id = ?` 过滤条件，而不是返回全量数据再让 LLM 筛选。

## 动手环节：为一个空 Agent 设计完整的工具集（代码级）

> **AI：** 指导学习者逐步完成，每步贴代码、每步验证。全程约 60 分钟。
> **总目标：** ① 为"电商客服 Agent"设计 4 个工具；② 每个工具走完粒度→参数→返回值→错误处理→幂等性五步审查；③ 写一份工具 Schema 设计文档。
> **核心约束：** 每个工具的 Schema 必须包含本文档要求的四条款：触发条件 / 参数格式说明 / 返回值格式模板 / 幂等性声明。

---

### Step 1：设计 4 个工具，每个走五步审查（25 分钟）

**任务：** 为"电商客服 Agent"设计 4 个工具：`query_order`（查订单）、`create_return`（创建退货单）、`search_product`（搜索商品）、`check_coupon`（查优惠券）。

**对每个工具回答 5 个问题：**

1. 粒度：这个工具对应哪个用户意图？能不能拆？该不该合？
2. 参数：必填几个？可选几个？总计几个？每个参数的 description 怎么写？
3. 返回值：返回什么字段？用什么格式？不返回什么？
4. 错误处理：参数校验检查什么？异常怎么返回？
5. 幂等性：这个操作是幂等的吗？不是幂等怎么处理？

**✅ 验证标准：** 4 个工具的五步审查全部完成，每个工具的 Schema 包含四条款。

---

### Step 2：写工具 Schema 定义（20 分钟）

**任务：** 用 Python 字典写出 4 个工具的完整 Schema，每个包含 name、description（含触发条件）、parameters（含 required 和格式说明）。

**✅ 验证标准：** 4 个 Schema 的 description 都包含"当用户...时使用"的触发条件，parameters 的 description 都包含格式说明（如"订单号，格式如 ORDER123"）。

---

### Step 3：写工具返回值模板（10 分钟）

**任务：** 为每个工具写一个返回值格式化函数，返回人类可读的文本而非 JSON。

**✅ 验证标准：** 返回值包含关键信息摘要 + 操作建议（如"可退货""已发货"），不含数据库字段名（如 stat/uid/ct），不含其他用户数据。

---

### Step 4：写非幂等操作的幂等方案（5 分钟）

**任务：** 针对 `create_return` 这个非幂等操作，写一个幂等处理方案。

**✅ 验证标准：** 方案包含具体的幂等键生成策略 + 重复请求检测逻辑 + 返回已有结果的处理方式。

---

## 判断力日志

> **AI：** 引导学习者写一条判断力日志，四段式（问题→决策→取舍→防什么失败）。

**提示要点：**

1. **问题：** 工具设计中最难的不是"写 Schema"，而是"决定一个工具做多少事"。工具粒度太粗，LLM 不敢用；太细，LLM 需要调 N 次才能完成任务。你用什么标准来判断粒度是否合适？

2. **决策：** 你决定用"一个工具 = 一个用户意图"作为粒度标准，而不是"一个工具 = 一个 API 调用"或"一个工具 = 一个业务场景"。这个决策的依据是什么？如果按"一个 API 调用"来设计，会遇到什么问题？

3. **取舍：**
   - 参数设计：可选的参数要不要暴露？暴露了 LLM 可能乱传，不暴露功能不完整。你怎么取舍？
   - 返回值：要返回"是否可退货"这个字段吗？返回了 LLM 可能直接告诉用户"可以退"（但实际还有金额限制）；不返回用户需要多问一轮。
   - 幂等性：每个工具都做幂等处理，还是只对写操作做？读操作做幂等有意义吗？

4. **防什么失败：**
   - 防"工具粒度太细导致 N+1 调用"——用户说"帮我退货"，Agent 调了 query_order → check_policy → create_return → notify_user 四个工具，每个都可能失败，成功率 = 0.95^4 = 81%。
   - 防"返回值太原始导致 LLM 瞎猜"——返回值是 `{"stat":2}`，LLM 不知道 stat=2 是"已发货"还是"已取消"，猜错了用户看到错误信息。
   - 防"非幂等操作无保护"——用户网络抖动连续点了两次"退货"，create_return 被调两次，生成两张退货单，后续退款处理全部混乱。

**写日志格式：**

```
## 判断力日志：Tool 粒度与返回值设计

### 问题
[描述你面临的问题]

### 决策
[描述你做了什么决策]

### 取舍
[描述你的取舍：哪些做了、哪些没做、为什么？]

### 防什么失败
[描述这个决策防止了哪些失败模式？]
```
