## 为什么需要 LLM Wiki？

> **真实场景：** 某团队给 Agent 接了 RAG 知识库，第一周效果很好。但三个月后，用户问"我们的 API 限流策略是什么"，Agent 从 200 篇文档里检索，返回了三段互相矛盾的答案——一段来自半年前的初版设计、一段来自上周的临时修补、一段来自今天刚更新的正式规范。Agent 不知道哪段是最新的、哪段是废弃的、哪段是权威的。**RAG 只负责"检索"，不负责"整理"。** 文档越多，噪声越大。

**RAG 是"每次去图书馆翻书"；LLM Wiki 是"把书读完，写一本自己的笔记"。**

**类比：做笔记的两种方式**

```
❌ 纯 RAG = 每次考试前冲到图书馆翻书
   考 10 次，翻 10 遍同一本书
   每次都从头找，每次都可能翻到不同版本
   笔记不存在，考完就忘
   成本随考试次数线性增长

✅ LLM Wiki = 上课记笔记，持续整理
   第一次学"Agent Loop"：记概念、画图、标重点
   第二次学"Tool Calling"：在 Loop 那页加引注"见 Tool Calling 页"
   第十次复习：打开笔记，结构清晰，交叉引用完整
   笔记本身在生长——第 10 条笔记写在前面 9 条的框架上
   成本：一次整理，持续复用
```

## 核心概念

### 第一讲：RAG vs LLM Wiki —— 解释器 vs 编译器

#### 核心比喻

|          | RAG（解释器）            | LLM Wiki（编译器）         |
| -------- | ------------------------ | -------------------------- |
| 模式     | 每次查询重新检索         | 先编译，再查询             |
| 知识状态 | 散落在原始文档里         | 蒸馏成结构化页面           |
| 积累     | 无——每次从头来           | 有复利效应——越积越厚       |
| 成本     | 随查询次数线性增长       | 一次编译，持续复用         |
| 一致性   | 可能查到多版本矛盾       | 编译时消解矛盾             |
| 适合场景 | 内容频繁变动、一次性查询 | 知识需要长期积累、反复引用 |

#### 为什么"编译器"这个比喻是精确的

```
编译器（LLM Wiki）：
  源码                    → 编译                  → 可执行文件
  （原始文档/对话/资料）     （Ingest：提取、结构化、    （Wiki 页面：有
                           消歧、建立交叉引用）        frontmatter、有
                                                    类型、有链接）

解释器（RAG）：
  源码                    → 每次解释执行
  （原始文档）               （Retrieve → Augment → Generate）
                          每次都要重新解析，不做持久化
```

> **关键洞察：编译器只编译一次，但可执行文件可以运行无数次。RAG 相当于每次都现场编译、现场运行——每次都有开销，且不保证两次编译结果一致。**

### 第二讲：Ingest / Query / Maintain 三操作

#### 操作全景

```
┌──────────────────────────────────────────────────────────────────┐
│                      LLM Wiki 三操作全景                           │
│                                                                  │
│   ① Ingest（编译）                                                │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  输入：原始资料（文档 / 对话结论 / 学生作业）              │   │
│   │  输出：结构化 Wiki 页面（带 frontmatter + [[wiki-link]]） │   │
│   │  步骤：                                                  │   │
│   │    1. 判定类型（concept / pattern / anti-pattern 等）     │   │
│   │    2. 提取核心信息（是什么 + 怎么用）                     │   │
│   │    3. 填写 frontmatter（type / id / prerequisites / tags）│   │
│   │    4. 建立 [[wiki-link]] 交叉引用                        │   │
│   │    5. 消歧：如果新内容和已有页面矛盾，标记并解决          │   │
│   └─────────────────────────────────────────────────────────┘   │
│                            │                                     │
│                            ▼                                     │
│   ② Query（查询）                                                │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  输入：自然语言问题                                       │   │
│   │  输出：最相关的 Wiki 页面 + 引用来源                       │   │
│   │  特点：读已编译知识，不重新检索原始文档                    │   │
│   │        可以限定 related 范围（只看相关概念）               │   │
│   └─────────────────────────────────────────────────────────┘   │
│                            │                                     │
│                            ▼                                     │
│   ③ Maintain（维护）                                             │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  自动检查：                                               │   │
│   │    - 交叉引用完整性（有没有死链？）                       │   │
│   │    - 页面一致性（有没有互相矛盾的描述？）                 │   │
│   │    - 孤岛检测（有没有没有任何 [[wiki-link]] 的页面？）    │   │
│   │    - 过期检测（last_updated 超过 90 天的页面）             │   │
│   │  输出：维护报告（哪些页面需要更新、哪些矛盾需要解决）     │   │
│   └─────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

#### 操作接口

```typescript
// 编译：把资料变成 Wiki 页面
async function ingest(
  source: string,
  target: string,
  schema: string,
): Promise<void>;

// 查询：基于 Wiki 回答
async function query(
  question: string,
  options?: {
    related?: string; // 限定在某个概念的关联范围内检索
    topK?: number; // 返回 top-K 结果
  },
): Promise<WikiQueryResult>;

// 维护：自动更新交叉引用
async function maintain(): Promise<MaintainReport>;

// 读取单个页面
async function getPage(path: string): Promise<WikiPage>;

// 更新页面
async function updatePage(path: string, content: string): Promise<void>;
```

> **教学要点：** Query 的 `related` 参数是关键设计。比如学生问"Agent Loop 有几步"，限定 `related: "agent-loop"` 后，只检索 agent-loop 概念页及其 `[[wiki-link]]` 链出的页面——不会被其他模块的无关内容干扰。

### 第三讲：复利效应 —— 为什么 Wiki 越用越强

> **核心洞察：第 100 份资料编译时，不是从零开始，而是建立在前面 99 份蒸馏出的知识结构上。**

#### 类比：写教科书

```
第 1 章写完：只有"什么是 Agent"的定义
第 2 章写完：第 2 章的"Tool Calling"引用了第 1 章的"Agent 定义"
第 5 章写完：第 5 章的"RAG"引用了第 2 章的"Tool Calling"（检索工具）
           → 三个概念形成了一个知识网

新来一个学生：
  RAG（每次检索）→ 翻 5 份文档，理解孤立
  Wiki（读编译后的）→ 一次看到三个概念的关联，理解更深

这就是复利效应：
  - 第 1 份资料：只建立了一个概念
  - 第 10 份资料：建立在前面 9 个概念的知识网上
  - 第 100 份资料：建立在前面 99 个概念的成熟知识体系上
```

#### 检索命中率的本质

```
Wiki 的检索命中率 = f(页面结构, 交叉引用密度, 内容质量)

一个孤岛页（没有 [[wiki-link]]）：
  → 只能通过自身关键词被命中
  → 命中率低

一个有 5 个交叉引用的页面：
  → 可以从 5 个不同入口被检索到
  → 命中率高

一个知识网（50 页互相链接）：
  → 任何一条查询都有多条路径命中
  → 命中率极高——这就是复利在检索上的体现
```

### 第四讲：[[wiki-link]] 交叉引用 —— 知识网的关节

#### 语法

```markdown
# 在概念页里引用另一个概念

参见 [[rag]] 的检索链路设计。

# 在 pattern 页里引用反模式

容易退化成 [[token-explosion]]：什么都往里写。

# 在反模式页里引用概念

根源在于没有理解 [[agent-loop]] 的停止条件。
```

#### 为什么交叉引用不是"锦上添花"而是"必须"

```
没有 [[wiki-link]] 的 Wiki = 一堆独立文件
  → 每页是信息孤岛
  → Query 只能靠关键词匹配命中
  → 换了种说法就搜不到
  → 本质退化成了"文件夹里的 Markdown"

有 [[wiki-link]] 的 Wiki = 知识图谱
  → 概念之间有显式关系
  → Query 可以从入口概念沿链接扩散
  → 换种说法也能通过关系链命中
  → 维护工具可以检测死链、孤岛、矛盾
```

#### 交叉引用的四个规则

1. **概念 ↔ 概念**：概念页之间必须互相链接（例：`[[rag]]` 与 `[[llm-wiki]]` 互相引用）
2. **反模式 → 概念**：每个反模式必须指向它违反的概念（例：`[[token-explosion]]` → `[[llm-wiki]]`）
3. **评分标准 → 概念**：每条评分标准必须关联它评判的概念
4. **项目 → 概念**：项目模板必须链接它训练的核心概念

### 第五讲：Write-Back —— 把对话变成知识

#### 什么是 Write-Back

> 一轮对话产生了可复用的结论时，把它写成 Wiki 页面，而不是留在聊天记录里。

这是 LLM Wiki 最核心的"增长机制"——Wiki 不是建好就完事的静态文档，而是**持续从对话中蒸馏知识**的活系统。

#### Write-Back 五步法

```text
1. 判定：这条结论下次还会用到吗？（只用一次的，不写）
   ✅ "评测 Agent 时，prompt 里必须写死评分维度名，否则维度会漂移"
   ❌ "今天天气不错"

2. 定位：归到哪个目录、属于哪种页面类型
   ├── 踩坑记录 → anti-patterns/（反模式）
   ├── 有效做法 → patterns/（设计模式）
   ├── 核心定义 → concepts/（概念）
   └── 评分维度 → validation/（评分标准）

3. 落页：frontmatter 写全（type / last_updated / id / tags）

4. 交叉引用：用 [[wiki-link]] 连回相关概念
   别让新页变成孤岛——孤岛页写了也检索不到

5. 记日志：log.md 记一行「新增/修改了什么」
```

#### Write-Back vs 不做 Write-Back

```
❌ 不写回：
  学生："Agent 循环卡住怎么办？"
  老师：解释了 5 分钟，讲清楚 max_iter 和 stop 条件
  一个月后，另一个学生问同样的问题
  老师：又解释了 5 分钟（或者换成另一个老师，解释了完全不同的 5 分钟）
  知识：0 积累

✅ 写回：
  学生："Agent 循环卡住怎么办？"
  老师：解释了 5 分钟
  系统：将结论编译为 anti-patterns/infinite-loop.md
  一个月后，另一个学生问同样的问题
  系统：Query → 命中 [[infinite-loop]] → 引用上一次蒸馏出的知识
  知识：被复用了
```

```markdown
# 多 Agent 协作

## 定义

多 Agent 协作是让多个 AI Agent 分工合作完成复杂任务。
不是"一个 Agent 做所有事"，而是"每个 Agent 专精一件事，通过路由调度协同"。

## 四种协作模式

- 顺序流水线：Agent A 输出 → Agent B 输入
- 并行分派：一个问题分给多个 Agent，汇总结果
- 辩论模式：两个 Agent 互相质疑，第三方裁定
- 层级路由：入口 Agent 分类 → 分发到专业 Agent

## 为什么需要多 Agent

单 Agent 的上下文窗口有限，职责混乱时输出质量下降。
多 Agent 每个只关注自己的领域，prompt 更短、输出更精准。

## 相关概念

- [[agent-loop]]：每个 Agent 内部仍然是 ReAct 循环
- [[tool-calling]]：Agent 之间通过工具调用传递结果
```

## 📝 分层测验

### 第一层：概念理解（选择题）

**1.** LLM Wiki 与 RAG 的本质区别是什么？

- A. Wiki 用 Markdown，RAG 用 PDF
- B. Wiki 是"编译一次、持续复用"，RAG 是"每次重新检索"
- C. Wiki 比 RAG 快
- D. Wiki 是 RAG 的另一种叫法

答案：B。编译器 vs 解释器是核心区别。A 是技术细节不是本质；C 不一定（看实现）；D 是错的，两者是不同模式。

**2.** 一篇新写的 Wiki 页面没有任何 `[[wiki-link]]`，后果是什么？

- A. 页面无法保存
- B. 它变成孤岛页，进不了 related 检索范围，写了也检不到
- C. 检索时会报错
- D. 没有后果，链接只是装饰

答案：B。孤岛页只能通过自身关键词被命中，无法从关联概念扩散检索到它。

**3.** 什么情况下应该用 RAG 而不是 LLM Wiki？

- A. 知识需要长期积累和反复引用
- B. 内容频繁变动、每次查询需要最新版本
- C. 需要建立知识之间的交叉引用
- D. 希望后续查询成本越来越低

答案：B。内容频繁变动时，编译跟不上更新速度，RAG 每次重新检索反而更准确。A、C、D 都是 Wiki 的优势场景。

### 第二层：动手题

**4.** 以下哪条对话结论应该 Write-Back 进 Wiki？选出并说明理由。

- (a) "今天的日期是 2026 年 9 月 22 日"
- (b) "System Prompt 里写角色时，用'你是 X'比'你扮演 X'效果好，因为后者暗示角色是临时的"
- (c) "帮我算一下 3 + 5"
- (d) "这个 API 的超时时间我设成 30 秒"

答案：只有 (b) 值得 Write-Back。判定标准：下次还会用到吗？(a)(c) 是一次性的；(d) 是配置不是知识；(b) 是可复用的 Prompt 工程经验，写成 pattern 后每个学生都能受益。
