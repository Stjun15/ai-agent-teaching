## 为什么需要知识库管理？

> **真实场景：** 某团队把 50 份 PDF 产品文档直接扔给 Agent，指望它"自己看"。结果：用户问"手机 A 的电池容量是多少"，Agent 回答"根据文档，手机 A 采用 5000mAh 电池"——但实际是 4500mAh。查了半天发现：Agent 把手机 A 和手机 B 的文档混在一起读了，因为切分时把两段不同产品的文本切到了同一个 Chunk 里。**知识库不是文档的"垃圾堆"，而是需要精心组织的"图书馆"——每本书放对书架，每段话标好来源。**

**类比：图书馆 vs 垃圾堆**

```
坏做法 = 把所有书撕成碎片，随机扔进一个大箱子
  → 用户要查"手机电池"，从箱子里随机抓一把碎片
  → 可能抓到手机A的电池数据 + 手机B的充电器数据 + 退货政策
  → Agent 用这些碎片拼出一个"看似合理但完全错误"的回答

好做法 = 图书馆
  ├── 分类上架：技术文档、产品手册、售后政策，分开放
  ├── 索引卡片：每本书的关键信息有索引
  ├── 来源标注：每段信息标注出自哪本书、哪一页
  └── 检索精准：用户要查"电池"，只从相关书架取书
```

## 第一讲：RAG 知识库核心流程

### 1.1 端到端流程

```
┌──────────────────────────────────────────────────────────────────┐
│                    RAG 知识库端到端流程                             │
│                                                                  │
│  ① 文档摄入（Ingestion）                                          │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ PDF/Word/Markdown/HTML → 文本提取 → 清洗（去噪/去重）      │   │
│  │ 为什么需要清洗？PDF 可能含页眉页脚、水印、乱码              │   │
│  └──────────────────────────────────────────────────────────┘   │
│         │                                                         │
│         ▼                                                         │
│  ② 文档切分（Chunking）                                           │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 长文档 → 多个 Chunk（每段 500-1000 tokens）                │   │
│  │ 关键参数：chunk_size（大小）、chunk_overlap（重叠）         │   │
│  │ 为什么需要重叠？防止关键信息被切在边界上                     │   │
│  └──────────────────────────────────────────────────────────┘   │
│         │                                                         │
│         ▼                                                         │
│  ③ 向量化（Embedding）                                            │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 文本 Chunk → Embedding Model → 向量（如 1536 维数组）      │   │
│  │ 为什么需要向量化？文字无法直接比较相似度，向量可以           │   │
│  └──────────────────────────────────────────────────────────┘   │
│         │                                                         │
│         ▼                                                         │
│  ④ 向量数据库存储                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 向量 + 元数据（来源、页码、时间）→ 向量数据库               │   │
│  │ 为什么不用普通数据库？向量相似度搜索需要专用索引（HNSW等）   │   │
│  └──────────────────────────────────────────────────────────┘   │
│         │                                                         │
│         ▼                                                         │
│  ⑤ 用户查询时检索                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 用户问题 → Embedding → 向量相似度搜索 → Top-K Chunk        │   │
│  │ 为什么是 Top-K 而不是 Top-1？多个 Chunk 提供更完整上下文    │   │
│  └──────────────────────────────────────────────────────────┘   │
│         │                                                         │
│         ▼                                                         │
│  ⑥ 注入 LLM 上下文                                               │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 检索到的 Chunk + 用户问题 → System Prompt → LLM 生成回答   │   │
│  │ 关键：标注来源，让用户知道信息来自哪里                       │   │
│  └──────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 实现：文档摄入与切分

**文件：`agent-platform/src/knowledge-base/document-processor.ts`**

```typescript
/**
 * 文档处理器
 *
 * 为什么切分比想象中重要？
 * 切得太小 → 语义不完整，检索到的片段没有上下文
 * 切得太大 → 检索精度下降，无关信息太多
 * 切分边界不对 → 关键信息被腰斩，两边都检索不到
 */
export class DocumentProcessor {
  /**
   * 递归字符切分器
   *
   * 为什么用递归而非固定大小？
   * 固定大小可能在句子中间切断 → "手机电池容量为" 和 "5000mAh" 分到两个 Chunk
   * 递归按优先级尝试分隔符：段落 → 换行 → 句号 → 空格 → 字符
   */
  async chunkDocument(
    text: string,
    options: ChunkOptions = {},
  ): Promise<Chunk[]> {
    const {
      chunkSize = 500, // 每段最多 500 字符
      chunkOverlap = 50, // 相邻段重叠 50 字符
      separators = ["\n\n", "\n", "。", ".", "，", ",", " "],
    } = options;

    const chunks: Chunk[] = [];
    let currentChunk = "";
    let chunkIndex = 0;

    // 按分隔符优先级递归切分
    const segments = this.recursiveSplit(text, separators);

    for (const segment of segments) {
      // 如果当前段加上新内容不超过 chunkSize，继续追加
      if (currentChunk.length + segment.length <= chunkSize) {
        currentChunk += (currentChunk ? " " : "") + segment;
      } else {
        // 保存当前 Chunk
        if (currentChunk) {
          chunks.push({
            id: `chunk-${chunkIndex++}`,
            content: currentChunk,
            index: chunkIndex,
          });
        }
        // 开始新 Chunk，包含 overlap 部分
        const overlapText = currentChunk.slice(-chunkOverlap);
        currentChunk = overlapText + segment;
      }
    }

    // 保存最后一个 Chunk
    if (currentChunk) {
      chunks.push({
        id: `chunk-${chunkIndex++}`,
        content: currentChunk,
        index: chunkIndex,
      });
    }

    return chunks;
  }

  /**
   * 递归切分：按分隔符优先级逐级切分
   *
   * 为什么按优先级？
   * 先按段落切（\n\n）→ 保持段落完整性
   * 再按换行切（\n）→ 保持句子完整性
   * 再按句号切（。）→ 保持语义完整性
   * 最后按字符切 → 兜底，确保不超 chunkSize
   */
  private recursiveSplit(text: string, separators: string[]): string[] {
    if (separators.length === 0) {
      // 没有分隔符了，只能按字符切
      return [text];
    }

    const separator = separators[0];
    const remainingSeparators = separators.slice(1);

    // 按当前分隔符切分
    const parts = text.split(separator).filter((p) => p.trim());

    if (parts.length === 1) {
      // 当前分隔符没切动，尝试下一个
      return this.recursiveSplit(text, remainingSeparators);
    }

    // 对每个部分递归处理
    const result: string[] = [];
    for (const part of parts) {
      result.push(...this.recursiveSplit(part, remainingSeparators));
    }
    return result;
  }
}

interface ChunkOptions {
  chunkSize?: number;
  chunkOverlap?: number;
  separators?: string[];
}

interface Chunk {
  id: string;
  content: string;
  index: number;
}
```

### 2.2 Parent-Child 分块（2026 新范式）

```
┌──────────────────────────────────────────────────────────────┐
│              Parent-Child 分块原理                             │
│                                                              │
│  传统分块的问题：                                              │
│    检索精度和生成质量是矛盾的                                  │
│    - 小 Chunk（128 tokens）→ 检索精准，但上下文不完整         │
│    - 大 Chunk（1000 tokens）→ 上下文完整，但检索不够精准       │
│                                                              │
│  Parent-Child 分块的解决方案：                                 │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Parent Chunk（父块）                                  │   │
│  │  ┌────────────┬────────────┬────────────┬──────────┐ │   │
│  │  │ Child 1    │ Child 2    │ Child 3    │ Child 4  │ │   │
│  │  │ 128 tokens │ 128 tokens │ 128 tokens │128 tokens│ │   │
│  │  └────────────┴────────────┴────────────┴──────────┘ │   │
│  │  检索时：用 Child Chunk 做精确匹配                      │   │
│  │  生成时：返回整个 Parent Chunk 给 LLM（完整上下文）      │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  效果：检索精度 ↑ + 生成质量 ↑，不再矛盾                       │
└──────────────────────────────────────────────────────────────┘
```

## 第三讲：向量化与检索

### 3.1 Embedding 模型选择

**文件：`agent-platform/src/knowledge-base/embedding-service.ts`**

```typescript
/**
 * Embedding 服务
 *
 * 2026 年主流 Embedding 模型对比：
 * - text-embedding-3-small: $0.02/百万tokens, 512维, 够用
 * - text-embedding-3-large: $0.13/百万tokens, 3072维, 精度高
 * - voyage-3-lite: $0.06/百万tokens, 1024维, 性价比好
 *
 * 为什么不是维度越高越好？
 * 维度高 → 存储大、检索慢，且精度提升边际递减
 * 512 维对大多数场景够用，3072 维用于高精度场景
 */
export class EmbeddingService {
  private model = "text-embedding-3-small"; // 默认性价比之选

  /**
   * 文本转向量
   * 为什么需要批量处理？
   * Embedding API 按调用次数计费，100 条单独调用 vs 1 次批量调用，成本差 100 倍
   */
  async embed(texts: string[]): Promise<number[][]> {
    const response = await openai.embeddings.create({
      model: this.model,
      input: texts,
      // 为什么可以批量？API 支持一次传多个文本，按 token 总量计费
    });
    return response.data.map((d) => d.embedding);
  }

  /**
   * 单条文本转向量（用于用户查询）
   */
  async embedQuery(query: string): Promise<number[]> {
    const response = await openai.embeddings.create({
      model: this.model,
      input: query,
    });
    return response.data[0].embedding;
  }
}
```

### 3.2 向量检索

**文件：`agent-platform/src/knowledge-base/vector-store.ts`**

```typescript
/**
 * 向量存储与检索
 *
 * 为什么用向量数据库而不是 PostgreSQL？
 * 向量相似度搜索（如余弦相似度）需要 ANN（近似最近邻）索引
 * 传统数据库的 B-Tree 索引不适合高维向量搜索
 */
export class VectorStore {
  /**
   * 相似度检索
   *
   * @param queryEmbedding 查询向量
   * @param topK 返回最相似的 K 个结果
   * @param minScore 最低相似度阈值（过滤不相关结果）
   */
  async search(
    queryEmbedding: number[],
    topK: number = 5,
    minScore: number = 0.7,
  ): Promise<SearchResult[]> {
    // 余弦相似度计算
    // 为什么用余弦相似度而非欧氏距离？
    // 余弦相似度关注方向而非大小，更适合文本语义比较
    const results = await this.db.query(
      `
      SELECT 
        id, content, metadata,
        1 - (embedding <=> $1) AS similarity  -- pgvector 的余弦距离
      FROM chunks
      WHERE 1 - (embedding <=> $1) > $2
      ORDER BY embedding <=> $1
      LIMIT $3
    `,
      [queryEmbedding, minScore, topK],
    );

    return results.map((r) => ({
      id: r.id,
      content: r.content,
      metadata: r.metadata,
      score: r.similarity,
    }));
  }
}

interface SearchResult {
  id: string;
  content: string;
  metadata: Record<string, any>;
  score: number; // 0-1，越高越相似
}
```

### 提示词教学：基于知识库的问答 Prompt

> **AI：** 不重讲六要素模板（真源：`03-AI协作构建\03-AI协作构建技能.md`；进阶：`06-AI能力-Prompt工程实战.md`），只讲知识库问答场景怎么填。

**① 场景**：知识库问答的 prompt 要解决两个核心问题——**"只依据检索到的文档回答"**（不编造）和**"标注来源"**（让用户知道答案来自哪里）。RAG 的知识库检索结果注入到上下文后，LLM 容易"偷懒"——看到多个 Chunk 内容矛盾时选一个编一个，或者完全不引用文档直接用训练数据回答。这个 prompt 就是把 LLM 锁在"只做读书笔记，不做自由发挥"的盒子里。

**② 六要素对照表**：

| 要素     | 知识库问答 prompt 填什么                                                                                                                                                                        |
| :------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 角色     | 知识库问答助手（只基于给定文档回答，不做自由发挥）                                                                                                                                              |
| 任务     | 基于检索到的文档片段回答用户问题，标注每条答案的来源                                                                                                                                            |
| 上下文   | 检索到的 Top-K Chunk（含来源标注：文件名、页码、更新时间）                                                                                                                                      |
| 约束     | ① 只依据给定文档回答，文档中没有的信息回答"文档中未找到相关信息"；② 多个文档信息矛盾时，列出矛盾并标注来源，不自行判断哪个正确；③ 每条事实性回答必须标注来源 Chunk ID；④ 不引用训练数据中的知识 |
| 参考     | 检索到的文档 Chunk 内容（已注入上下文）                                                                                                                                                         |
| 输出格式 | 自然语言回答 + 每条回答末尾标注来源（格式：`[来源：{文件名} 第{页码}页]`）                                                                                                                      |

**③ 示例 Prompt**（知识库问答，可直接用）：

```
你是知识库问答助手。你的回答必须**仅基于**以下检索到的文档片段，不得使用任何外部知识。

检索到的文档片段：
{retrieved_chunks}

回答规则：
1. 只基于以上文档片段回答，文档中没有的信息回答"文档中未找到相关信息"
2. 多个文档片段信息矛盾时，列出矛盾并标注各自来源，不自行判断哪个正确
3. 每条事实性回答末尾标注来源，格式：[来源：{文件名} 第{页码}页]
4. 不确定的信息标注"（待确认）"
5. 不引用你的训练数据中的知识，即使你知道答案——只以文档为准

用户问题：{question}
```

**④ 反例 + 为什么**：

```
知识库问答 prompt：'请根据文档回答用户问题。'   // ❌
```

错在哪：① 没锁"只依据给定文档"——LLM 看到检索结果不完整时，会用训练数据中的知识（如"iPhone 15 Pro 电池容量 3274mAh"）来补充，但这个数字可能和实际文档不一致；② 没要求标注来源——Agent 回答"根据文档，退货政策是 7 天无理由"，用户追问"哪个文档写的？"时 Agent 无法回答，RAGAS 评测的 faithfulness 指标直接挂；③ 没处理矛盾——两个文档分别说"退货期限 7 天"和"退货期限 15 天"，LLM 可能随机选一个或自己编一个"10 天"，用户被误导。

**⑤ 完成标准**：能独立写出包含**只依据给定文档 / 矛盾标注来源不自行判断 / 每条事实标注来源 / 不引用训练数据**四条款的知识库问答 prompt。

## 2026年最新动态（截至2026年8月）

### 2026 年 RAG Chunking 七大策略

| 策略                     | 核心思想                          | 最佳场景       |
| ------------------------ | --------------------------------- | -------------- |
| 固定大小                 | 按 Token 数切分                   | 通用文档       |

| 结构感知分块             | 保留标题/表格/代码块为原子单元    | 技术文档       |
| **Parent-Child 分块**    | 检索用小 Chunk，生成用大 Chunk    | 长结构化文档   |
| **Contextual Retrieval** | 每个 Chunk 前追加文档级上下文摘要 | 多文档知识库   |
| **动态分块**             | 内容自适应 + 查询自适应           | 混合类型知识库 |
