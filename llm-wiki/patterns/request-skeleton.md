# 最小请求骨架

## 什么时候用

第一次调 LLM API，或者改了半天调不通的时候。

先把请求压到**能跑通的最小形态**，再一个一个加字段。反过来做（一上来就写满参数）的典型后果是：报错时你不知道是哪个参数导致的，只能逐个注释掉试。

## 写法

```text
请求 = 模型名 + 消息数组

messages:
  - system: 一句话说清身份与边界
  - user:   这一次要它做的事
```

要点：

- `model` 与 `messages` 是**唯一必填**的两个字段，其余都有默认值；
- system 消息只写「不变的部分」（身份、风格、边界），当次任务放在 user 里；
- 多轮对话 = 把历史消息**整段**放进 `messages`，不是把上一次的答案粘进新问题。

## 为什么有效

模型看到的是一串带角色的消息，不是「一句话」。角色写清楚了，同一句 user 话会得到稳定的回答；角色不写，回答风格每次都不一样 —— 这不是模型心情问题，是输入里根本没写。

而「最小形态先跑通」把调试变量压到两个，出错时能立刻二分定位。

## 容易退化成什么

- 退化成 [[missing-params]]：堆了一堆参数，其中一半是抄来的、自己也不知道作用；
- 退化成把上下文塞进 system：system 越来越长，最后变成一坨每次都要重发的需求文档，见 [[token-explosion]]。
